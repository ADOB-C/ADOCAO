# 2e9：本项目的当前目标

> **一句话**：让 ADOCAO 能在普通机器上打开**约 21 亿层（2³¹−1 = 2,147,483,647）**的谱面 ——
> 加载不 OOM、能 seek 到任意层、播放不掉帧 —— 而且**常驻内存与层数 n 解耦**（n 从 1e6 长到 2³¹，
> RSS 基本不变），同时**现有的所有验收在每个阶段保持绿色**。
>
> 本文件是**目标与验收**的单一出处；`docs/scale-1e8-to-2e9.md`（39 KB）是**分析/实测**长文，
> `TODO.md` 是**任务清单**，`docs/adocao-format.md` §8 是**容器侧设计**。三者不重复。

---

## 1. 为什么是 2³¹−1

* 它是**32 位有符号**的天然上限：越过它，一切 `int` 索引、`GLsizei` 单次绘制、`FastAction::floor`
  都得换类型。所以"摸到 2³¹−1"= **把 32 位假设全部清算干净**，是个有明确边界的目标，而不是"越大越好"。
* 现实参照：本地最大的谱 `primer-final` 是 **6,841 万层 = 目标的 3%**（`docs/scale-1e8-to-2e9.md` §14）；
  MYC 677 万层、audio-as-chart（`Unity.wav_rate`）1,100 万层且**逐采样事件**。3% 是实验室的极限，
  所以边界的验证**只能靠纯函数单测 + 反面对照**（见 §5 纪律）。

## 2. "做到了"的可测定义（DoD）

| # | 判据 | 怎么量 | 现状 |
|---|---|---|---|
| D1 | **内存与 n 解耦**：n 从 6.8e6 → 6.8e7 → 2³¹，常驻 RSS 基本不涨（涨的只有 checkpoint 索引与窗口） | 真无头加载 + 峰值 RSS（`adocao image` 只加载不出图） | ❌ 现在线性（MYC **212 B/层**、峰值 1436 MB） |
| D2 | **任意层 O(1)~O(log n) seek**：跳到第 k 层不需要重放全谱 | 从 checkpoint 重建窗口，量 seek 延迟 | ❌ 无 checkpoint |
| D3 | **播放预算**：可见实例 ≤ 60 fps 的容量线（重绘口径 **159K**/几何口径 489K） | `docs/scale-1e8-to-2e9.md` §8 的标定（34.12 ns/实例几何下限、100~105 ns 重绘受限） | ⚠️ 容量公式已有，未接窗口化。**2026-10-16 实测到「每帧贵在哪」**（`sample` 主线程 2284 样本）：`FloorWindowCache::materialize` **824（36%）** + `computeFloorWindow` 446+231+103（内层是逐砖 `__sincos_stret`）+ `deriveRange` 353 —— 即**每帧成本 ∝ 命中粗块数 × 4096 层的三角函数**，而且**全在主线程**（共享窗口缓存必须主线程 pin，并行剔除段借不到并行度）。宽视野下命中 ~700 块 → 单次重建 **160~240 ms** ✗（p50 仅 6~8 ms，但 26~42% 帧 >16.7 ms）。三步打法（都不改出图）：① **窗口物化并行到 worker**（各块独立）预期 ~8~10×；② **位置提供者加 512 层细锚点**（现在只能从 4096 锚点走 4096 层 trig）再 ~8×；③ 到 2³¹ 时「同屏密度」仍是主项 → 见 ⑦ 的 LOD 边界 |
| D4 | **零行为变化**：现有验收全绿 —— ctest（当前 18 个）、40 份 fixture 逐位对拍、**像素门槛 51/51 逐字节**、core-purity、shader-fallback、无绝对路径 | 每阶段全跑 | ✅ 基线 |
| D5 | **规模律可复现**：每条规模结论都留下"可重跑的命令 + 数字 + 证据等级" | 文档留痕 | ✅ 本仓库惯例 |

**目标态的算账**（`docs/scale-1e8-to-2e9.md` §3/§8.2）：

* 常驻只留**稀疏随机访问索引**：若保留"每层 O(1)"契约，最小集 ≈ **36 B/层**（position 16 + times 8 +
  angles 8 + BPM 4 + CW 1 bit）—— 2³¹ 层就是 **77 GB** ✗，所以**不能靠"每层都常驻"**；
* 真正的出路是 **每 4096 层一条 37 B 的 checkpoint（= 0.009 B/层）+ 窗口重算**：
  2³¹−1 层的索引只要 **19.4 MB**，其余（angleData / 时间 / actions / 每砖数组）都可窗口化或可重算。

## 3. 现状基线（2026-10-11）

**靶场（本地真谱）**

| 谱 | 层数 | 特点 |
|---|---|---|
| `primer-final` | 6,841 万（**3%**） | 最大；修完 `Tile` 容量 2× 坑后 GUI 播放换出量 +296 MB → **0**，峰值 RSS 5.9 GB |
| `Unity.wav_rate`（audio-as-chart） | 1,100 万 | **逐采样** `SetHitsound`（1,099 万事件）、文本 1.47 GB |
| MYC | 677 万 | 事件密度 ≈0.9/层；真无头峰值 **1436 MB / 212 B/层**（mesh ≈430 MB）|
| angles360 / The Moon | 万级 | 人工/正常谱参照 |

**每层字节账**（实测，`docs/scale-1e8-to-2e9.md` §2）

* `Timeline` 恒定 7 支数组 = **32.125 B/层**（`tileStartTimes` 8 B 起）；
* 加载期峰值 **212 B/层**（MYC 口径）→ 2³¹ 层 ≈ **455 GB** ✗ —— 这就是 D1 要打的那一仗；
* 已经省掉的：层距两条 `vector<float>`（8 B/层，2³¹ 层 = 17 GB）→ 层数 + 两个标量；
  `Tile` 容量 2× 坑（24 B/层 → 48 B/层）、`setSpeedByFloor` 无条件 1.2 GB、`angleData` 预留按密度估。

**时间账**：MYC 无头 **1.39 s / 1473 MB**（`parseNumber` 的 `e` 边界 bug 修完后的数字；修前 4.60 s / 4943 MB）。
`actions` 分块并行阈值 32 MB~768 MB 在大谱上**永远不生效**（§5.4）。

**32 位账**：`#0 阶段 1–2 已完成` —— `core/util/CountLimits.hpp`（`fitsInt32`/`toInt32Checked`）
+ `tests/limits_test.cpp`（ctest `limits`，13 条断言含**反面对照**），§6 表里所有 `(int)size()` 站点
改成"int64 算、收窄前显式判、装不下就 `LOG_E`"。**Timeline 现在对 >int32 层是明确拒绝**（不是静默坏）。
**阶段 3 未做**：循环索引、`floor` 自身的类型（`FastAction::floor` 一族才是最深那层假设）、`GLsizei` 分批。

**容器账**（`.adocao` v2 已落地，v3 只落了诊断）：

| 谱 | 明文 | xz -9e | `.adocao` | vs xz |
|---|---|---|---|---|
| MYC | 641 MB | 2.18 MB | **6,120 B** | **356×** |
| The Moon | 16.4 MB | 122 KB | **3,544 B** | **34.4×** |
| Unity.wav_rate | 1.47 GB | 49.4 MB | **20.1 MB**（1.92 B/层）| **2.34×** |
| かめりあ - QuomodocunquizE | 3.62 MB | 136 KB | **108,928 B** | **1.25×** |

**"最先不可行的一环"（2026-10-15 已修，见 §4 ①）**：`.xz` 的**流式窗口路径会静默放弃、退回整份解压** ——
`Unity.wav_rate` 上默认 `ADOCAO_WINDOW_KB=4096` **3/3 拒收**（8192 才收），代价 **+1271 ms / +482 MB**；
对 1e8 层文本而言，"退回去做一次连续分配"等于**在任何一层建起来之前就必然失败**
（`docs/scale-1e8-to-2e9.md` §4）。

**真因（2026-10-15 定位并修复，`strtod` 那条归因是错的）**：`parseNumber` 的**指数回退**。
当半窗正好在 `e` / `e±` 之后用完时，它把 `q` 退回指数标记、**当作"光秃秃的 e 不算指数"**，
于是 ① 提交了一个**截断错值**（`4.547473508864641` 而不是 `4.547473508864641e-13`）；
② 残留的 `e` 被 carry 到下一窗，而下一窗的第一个字节就是 `e`（`parseNumber` 立刻失败）
→ 整窗原样 carry → 半窗被自己占满 → `ArchiveStream::stuck()` → 静默回退整份解压。
audio-as-chart 的层值**全是指数写法**，所以必然命中；8192 KB 只是换了边界相位、恰好绕开。
现在"缓冲区在 `e`/`e±` 后用完"直接返回 false（= 这里没有完整数字），窗口会把它 carry 到下一窗重放。
永久用例：`windowExponentBoundarySelfTest()`（定点相位 + 8 种半窗相位的数字形式扫描，逐位对拍）。

## 3.5 相机与 ColorTrack 对 2e9 的影响（2026-10-17 实测）

先说结论：**事件本身都是 O(事件数)，不会把 D1 打穿**；真正要防的是三件事 ——
① 相机建造依赖**密集** `tileStartTimes`/`tileBPMs`（8+4 B/层）；② `ColorTrack` 的事件数
**可以随层数线性长**（逐层 `justThisTile`），以及**逐可见砖**的颜色开销在 LOD 上限（26.2 万）会吃掉帧预算；
③ `TweenColor` 的逐砖时间查询应改成**每事件预计算**。

### 实测数字（Apple M5，2026-10-17）

| 量 | 值 | 怎么测 |
|---|---|---|
| `sizeof(CameraEvent)` / `sizeof(ColorEvent)` | **64 B / 160 B** | 探针 `sizeof`（字符串都是 SSO，无堆分配） |
| ColorTrack 事件数 | The Moon **2600**（justThisTile 0）、Singularity **1486**、MYC **0** | `level.adofai` 直接数 + 探针 |
| 每事件常驻 | 2600 → **0.42 MB**；1e6 → **160 MB**；**2³¹ 逐层 → ≈320 GB ✗** | 160 B × 事件数（推导） |
| `colorEventAt`（2600 事件，二分） | **101 ns** | 探针 20 万次随机层 |
| `tileColorsAt`（默认段，无事件） | **50 ns** | 纯 settings 谱 |
| `tileColorsAt`（The Moon，2600 事件） | **178 ns** | 同上 |
| `tileColorsAt`（带一条 fade 事件） | **65 ns** | 小谱（时间线只有一块 → 窗口缓存不抖） |
| `CameraTimeline::build`（The Moon，31 键） | **<0.1 ms** | 同探针 |
| `Timeline::findTileIndex` | **73 ns** | 窗口化后仍是"锚点二分 + 块内 4096 扫" |

**外推**：26.2 万可见实例（`kMaxInstances`）× 50~178 ns = **13~47 ms/帧**；
如果颜色按老路逐砖算，D3 的 16.7 ms 预算在"整张一帧"档会被吃掉——这是颜色对 2e9 的**主要风险**。
加载侧：`TileMesh::build` 的逐砖 `styleOfTile`（二分）≈ **100 ns/层** → 60 万层 60 ms、
6,841 万层 **6.8 s**、2³¹ 层 **200 s ✗**（在本来就 O(n) 的形状分组之上再加一笔）。

### 相机的 2e9 阻塞点（按严重度）

1. **依赖密集数组**：`CameraTimeline::build(level, tileStartTimes, tileBPMs)` 直接索引
   `tileStartTimes[floor]` / `tileBPMs[floor]`（`core/camera/CameraTimeline.cpp` 的 `timeAt`/`bpmAt`）。
   2³¹ 层时这两条数组是 **17 GB + 8.6 GB**，而 ③ 的目标正是让它们不存在。相机只在 **K 个事件层**
   上取值 → 改成收 `const Timeline&`、用窗口化 `startTimeAt()/durationAt()/bpmAt()`，成本 **O(K log n)**，
   与 n 解耦。
2. **`entryBeat` 是 8 B/层的临时数组**：只要出现 **Floor 模式**的 RepeatEvents，`computeEntryBeats()`
   就 `vector<double> eb(n)`（2³¹ → **17 GB**）——而且它消费的正是密集 `tileStartTimes`。
   实际只用到"展开后的 targetFloor 与 baseFloor 两点的差值" → 改成从 checkpoint 按点求值即可。
3. **重复展开没有上限**：`for (rep <= repetitions)` 没有 cap；Beat 模式又不受 `targetFloor < totalTiles`
   约束 → `repetitions = 1e9` 时 `m_keys` 直接爆（每个 CameraKey 还带着 `std::string tag`）。
   需要 `kMaxCamKeys`（建议 20 万）+ `LOG_W` 截断 + 反面对照。
4. 每帧成本本身很小：`update()` O(1)；`seek()` O(K) 重放（K 被 cap 后 ≤20 万，仍可能几十 ms，
   但只在跳转时付）。存储 64 B/键，与 n 无关 ✓。

### ColorTrack 的 2e9 账

1. **事件数可以随 n 长**：持久事件通常几十~几千条（实测 2600/1486/0），但 `justThisTile` 允许**逐层**
   一条 → 2³¹ 层 ≈ 320 GB ✗。需要"按块/按 floor 索引 + 上限"（和 actions 的 `ActionIndex` 同思路），
   或明确拒绝/截断（带 `LOG_W`）。
2. **逐可见砖的每帧成本**：`tileColorsAt()` 每次会 `colorEventAt()`（二分 ~100 ns）+ 解析 hex/复制
   `TileColorConfig`（7 个 SSO 字符串）→ 50~178 ns/砖。修法（不改语义）：
   * 先按**段**预解析：每段一条 `{fill, stroke, opacity, style, type, pulse}`，静态类型整段同色；
   * 绘制列表是**按砖号升序**的 → 用"段指针随列表前进"代替每砖二分：O(可见 + 段数)；
   * 只有 `pulse=Forward/Backward`（颜色随 floor 变）才逐砖算；Glow/Blink/Rainbow/Volume 每段一次；
   * 预期每砖降到 ~5 ns 量级（26.2 万 → **1~2 ms**），D3 才稳。
3. **TweenColor 的逐砖时间查询**：`tileColorsAt(..., timeline)` 现在每砖调
   `timeline->startTimeAt(e->floor)` / `durationAt(e->floor)`。同段内的砖查的是**同一个事件层**，
   单块缓存命中 → 实测只 +15 ns；但如果可见列表跨多个段/块，就会重演"拖尾 1 秒/帧"那类
   **单块缓存抖动**。修法：在加载时给每个 `ColorEvent` 预存 `startTime` 与 `beatSeconds`（O(K)）。
4. **RecolorTrack 的块索引**（2026-10-17）：每 4096 层一块、块内按触发时间排序；内存 =
   `(n/4096) × vector` 的头（2³¹ ≈ 524k 块 × 24 B ≈ **12 MB**） + Σ覆盖条目（上限 4M 条 ≈ 16 MB，
   超了截断并 `LOG_W`）。查询 O(块内事件数)，与 n 无关 ✓；但**逐层 justThisTile 式的超大范围**
   仍会让条目线性长 —— 需要"按块懒建"才彻底解耦。
5. `.adocao` 的 `Colour` 段是 **32 B/事件（v3）/ 50 B（v4，含 RecolorTrack 范围）**（相机段 38 B/事件）→ 事件少时无感；逐层事件时
   容器本身也会线性膨胀，和 ③ 的"按块"方向一致即可。
5. **style 进形状键**（`GeoKey` 加 3 bit）本身是 O(唯一角度 × style)，不是 O(n) ✓；但它让
   `TileMesh::build` 的逐砖循环多了一次 `styleOfTile` 二分（100 ns/层）→ ③ 的"按窗口建 mesh"
   需要把 style 也做成**按块的段索引**。

### 建议的落地顺序（与 §4 的 ③/④ 对齐，不单开阶段）

1. 相机：`CameraTimeline::build` 改收 `Timeline`（窗口化取值）→ 去掉密集数组依赖；
   `entryBeat` 按点求值；加 `kMaxCamKeys`。验收：The Moon/Singularity 相机金标（已有）+
   一个 `repetitions` 超限的反面 fixture。
2. 颜色：每段预解析 + 段指针批量 + 事件级 `startTime/beatSeconds` 预计算；再加 `ColorTrack`
   数量上限/窗口化索引。验收：`tile_color_test` 的语义用例不变 + 一个"26 万可见"的帧时探针
   （目标：颜色部分 ≤2 ms）。
3. 之后才谈 ③ 的渲染侧 windowed provider —— 相机/颜色都不再持有 O(n) 数组，才能把 D1 真正落地。

## 5. 纪律（这些是铁律，不是建议）

1. **绝不静默截断**：计数/长度一律 int64；必须交给 32 位 API 时走 `fitsInt32`/`toInt32Checked`，
   装不下就 `LOG_E`。**本地造不出 2³¹ 层**（最大只有 3%），所以边界只承认**纯函数单测 + 反面对照**。
2. **零行为变化**：2³¹ 以下任何改动都必须让 ctest / 39 fixture 逐位 / **像素门槛 51/51** 全绿
   （`#0 阶段 2` 就是这么验收的：`adocao image` MYC 64×64 md5 相同）。
3. **像素/渲染类问题先出差异图再谈实验**；抓帧路径不许有"由帧时间反馈决定的量"。
4. **基线不入库、不放 `/tmp`**：像素基线在 `~/Projects/.ADOCAO/gate/baseline`，临时抓帧留工作区内。
5. **每条规模结论都要留"命令 + 数字 + 证据等级（实测/推导/外推）"**，并且**能重跑**。

## 6. 非目标

* 不重写渲染器、不换图形 API（Vulkan 版在 `../ADOCAV/`，是另一条线）。
* **不为 2³¹ 牺牲现有体验**：n ≤ 1e7 的谱，CPU/内存/加载时间不许变慢（D4 就是这条的守门员）。
* 不追"最大层数"这个数字本身：目标是**把 32 位假设清算干净**，让规模律变成可推导的。
