> 填好 `LevelData` 后与两条 JSON 路径**共用同一个 `finishLoad()` 收尾**。
> 端到端验证：MYC 用 `.adocao` 与用明文 JSON 出的 64×64 PNG **逐字节相同**
> （md5 `8fdbed25f383aaabea32d0677f89eae1`，6,770,913 层）。

## 0. 为什么要有这个格式

真实谱面大到无法传播：`primer-final.adofai.xz`（68,411,078 层）**xz -9e 之后仍是 357 MB**，
未压缩 7.38 GB；MYC 明文 611 MB。目标是把这类谱面压到能分发的体量，且**逐位无损**。

先算清楚现状的账（实测）：

| 谱 | 未压缩 | xz -9e | 每层 |
|---|---|---|---|
| primer（68.4M 层，118 blocks）| 7.38 GB | 357 MB | 115.7 → 5.47 B |
| Unity.wav_rate | 1.58 GB | 49.4 MB | 143 → 4.5 B |

结论：xz 对**文本 JSON** 已经很强，单纯"换成二进制再 xz"赢不了多少（二进制 double 还丢掉了
十进制文本的公共前缀，可能更差）。真正的杠杆是**领域编码**。

## 1. 设计原则

**列式存储 + 每列按其"取值基数"选编码。** 与谱面来源无关：

* MYC 的 6,770,912 个 `angleData` 值里只有 **52 个不同值**（二元组 293/2704、三元组 682，
  最常见三元组 `(13,25,13)` 出现 850,292 次）→ 字典 + 6 bit 下标；
* action 各列的基数同样很小：`bpmMultiplier` 10、`beatsPerMinute` 9、
  `angleOffset`/`rotation`/`opacity` **各只有 1 个取值**（→ 整列省略），`floor` 单调（→ 差分）。

> 早期草案里有一个"音频谱存 PCM/int16"的机制，**已删除**：那是 `Song.adofai`
> （audio-as-chart 工具）专有的，真正的观赏谱不长那样。字典编码顺带覆盖了它
> （音频谱的取值集合就是 int16 的 65536 个 → 2 B/层），而且不需要任何"可逆性证明"。

三条硬规矩：

1. **逐位无损**：double 列按**位模式**建字典（`-0.0` / `NaN` 也原样往返）；解码出来的 double
   位模式必须与输入完全相同。**不改变任何数值语义**，所以"浮点精度规则"不受影响 ——
   我们只改"表示"，不改"值"。
2. **编码器自检**：每次编码都先算候选、再解回来逐位比对，取"能用且最小"的那个；
   任何输入最坏只是退回 `Raw`，**不会编错**。
3. **失败必须响亮**：crc 坏 / 截断 / `version` 不符 / 未知 codec / 越界下标 → 明确失败，
   **绝不静默回退**（这条被 2026-10 的两次"静默回退让测试全绿"教训逼出来）。

另有一条分工：`writerCommit` / `inputHash` **只作溯源**，**绝不作兼容闸门** ——
版本门禁只认 `version`。没有 git 的构建写全 0 并标 unknown，**不影响可读性**。

## 2. 文件布局

```
Header (76 B) | SectionEntry × sectionCount (40 B each) | padding → 8 B 对齐 | 各段载荷
```

所有整数**小端**、**定宽**；段偏移 **8 B 对齐**（为将来的 mmap 直读）；段大小与元素数一律 `u64`
（从格式层消除 2^31 边界）。

### 2.1 Header（76 B）

| 偏移 | 类型 | 字段 | 说明 |
|---|---|---|---|
| 0 | char[4] | `magic` | `"ADO1"`，接入 `core/level/ByteSource.cpp::sniffLevelArchive` |
| 4 | u16 | `version` | 当前 **2**；**唯一的兼容闸门**（v2：稀疏载荷列 + 段级压缩）|
| 6 | u16 | `flags` | 保留（0）|
| 8 | u16 | `sectionCount` | |
| 10 | u16 | `reserved` | 0 |
| 12 | u64 | `fileSize` | 全文件字节数（截断检测）|
| 20 | u32 | `headerCrc` | 覆盖"头（本字段按 0 参与）+ **整张段表**"|
| 24 | u8[20] | `writerCommit` | 写入方 git commit 的**原始 20 字节**（构建期由 `git rev-parse HEAD` 注入，见下）；全 0 = unknown（没有 git 的构建）|
| 44 | u8[32] | `inputHash` | **内容指纹**：前 8 字节 = `FNV-1a-64`（小端），其余 24 字节写 0 |

**内容指纹（`inputHash`）的准确算法**（别的实现按这个算就能逐字节对上）：

* `FNV-1a-64`：`h = 1469598103934665603`（offset basis）；对每个字节 `h ^= b; h *= 1099511628211`；
* 覆盖范围 = **按写入顺序**的每一段：先段 id（1 字节），再该段的**未压缩**内容（`rawSize` 字节）；
* 所以它与压缩器、与构建**无关** —— 同一份谱在任何实现里都得到同一个指纹（可用于去重/溯源）；
* 结果按小端写进前 8 字节，后 24 字节写 0（留出将来换更宽哈希的余地）；
* 读取方**不看**这个字段，也**不许**拿它当兼容闸门。

**`writerCommit` 的注入方式**：根 `CMakeLists.txt` 在 configure 时跑 `git rev-parse HEAD`，
只给 `adocao_archive` 目标加 `-DADOCAO_GIT_COMMIT=<40 位十六进制>`；写入方把它解码成 20 原始字节。
拿不到 git（tarball / 离线构建）时该宏不存在 → 写 20 个 0。注意它记的是**构建**的 commit
而不是打包那一刻的 ✓ —— 这正是"写入方"的含义；也意味着**跨构建**两次打包会有这 20 字节的差异
（同一构建内仍然逐字节相同，`archiveRoundTrip` 断言的就是后者）。

### 2.2 SectionEntry（40 B）

`id(u8) | codec(u8) | flags(u16) | offset(u64) | compSize(u64) | rawSize(u64) | elemCount(u64) | crc32c(u32)`

* `crc32c` 覆盖该段 `compSize` 字节（Castagnoli；`"123456789"` 的标准检验值 `0xE3069283`）。
* `codec` 是 `Raw` / `SectionZstd` / `SectionXz`（v2 起支持两者）。2026-10-22 起打包器
  **两种压缩器都允许、级别可调**：`--compress=auto|zstd|lzma|none`、`--level=N`
  （0 = 编码器默认：zstd 19 / lzma 9|EXTREME）。`auto` 对每段**两个都试、取更小**；
  段 <256 B 或压不小就存 `Raw`。实测 Hello 2025：zstd-19 19,344 B、lzma-9e **18,480 B**、
  auto **18,352 B**、zstd-3 23,560 B、none 174,496 B —— lzma 在这张谱上又小又更快。
  `Raw` 时段内是**自描述**的列流（每个列头带自己的 codec）。
* 未知 `id` 一律跳过（前向兼容）。

### 2.3 段

| id | 段 | 内容 |
|---|---|---|
| 1 | `Settings` | 定长记录（见 §3.1）|
| 2 | `StringPool` | `u32 count` + 每项 `u32 len + bytes`；`v[0]` 必须是空串 |
| 3 | `AngleData` | **一列 double**（§4）|
| 4 | `Actions` | `u32 columnCount(=6)` + 每列 `u64 byteLen + bytes`。**v2 起 `strId`/`val1`/`val2` 是稀疏列**：列内容 = `u32 typeMask` + `u64 usedCount` + 一列（只含掩码内的类型）；掩码自描述（某类型在这一列出现过非默认值即入掩码），读取方按事件顺序只在掩码命中时取下一个值，其余取 0 —— 顺序与语义逐位不变 |
| 5 | `PathData` | `u64 len + bytes`（仅当非空）|
| 6 | `Preserved` | 未识别成员的原始字节 —— **待做**（今天这些本来就被丢弃；注意 `MoveCamera`/`RepeatEvents` 已走 9/10 段，不在这里）|
| 7 | `Derived` | 预计算/检查点 —— ✅ v3 起写（§8.11）|
| 8 | `ActionIndex` | 按层索引 —— ✅ v3 起写（§8.12 之后的 ActionIndex 小节）|
| 9 | `Camera` | **MoveCamera 富事件**，每记录 38 B（§3.4）。仅当谱面有运镜时写 |
| 10 | `Repeat` | **RepeatEvents**，每记录 19 B（§3.5）。仅当谱面有重复事件时写 |
| 11 | `Colour` | **ColorTrack**，每记录 32 B（§3.6）。仅当谱面有颜色事件时写 |

**只存输入，不存派生数据**：`Tile::position`（全局前缀和）、`direction`、`tileBPMs`、
`Timeline` 全部由 `angleData` + `actions` 重算。

## 3. 各段细节

### 3.1 Settings 定长记录

字段顺序固定（打包确定性）：`version(i32) | bpm(f32) | offset(f32) | countdownTicks(i32) |
zoom(f32) | rotation(f32) | relativeTo(u16 池下标) | position[2](f32) | hitsound(u16) |
hitsoundVolume(f32) | trackColor(u16) | secondaryTrackColor(u16) | backgroundColor(u16) |
stickToFloors(u8) | planetEase(u16) | trackDisappearAnimation(u16) | trackAnimation(u16) |
beatsBehind(f32) | beatsAhead(f32) | songFilename(u16 池下标) | pitch(f32) | legacyCamRelativeTo(u8)`

* **末尾的 `pitch`(f32) + `legacyCamRelativeTo`(u8) 是 2026-10-17 追加的**（运镜要用：pitch
  同时缩放事件时长与跟随速度，legacy 开关是老语义）。读侧同样按"尾部还在才读"处理。
* **`songFilename` 也是 2026-10-17 追加的**（ADOCAO-E 另存/重打包要 `.adofai` 的 `"song"`）。
  追加在**末尾**是为了双向兼容：读侧 `parseSettings()` 只在 `off + 2 <= 段长度` 时才读它
  （旧文件没有这两个字节 → 保留默认值，不是坏数据）；旧读者按原有字段顺序读完就返回，
  尾部多余字节本来就被忽略。因此**不用** bump 版本号。
* `f32` 按**位模式**原样存（float 列必须逐位无损）。
* 未知 settings 键与今天两条解析路径的行为一致（本来就只读已知字段）；无损回写靠 `Preserved` 段。

### 3.2 StringPool

**`actionStrTable` 的原序必须保留**（`FastAction::strId` 就是它的下标）；settings 用到的字符串按
固定顺序追加到末尾。`v[0]` 是空串（`strId = 0` 的约定）。

### 3.3 Actions（列式）

固定 6 列，顺序：`floor(int64) | type(u32) | strId(u32) | flag(u32) | val1(u32) | val2(u32)`。

* `floor` → `encodeIntColumn`（单调 → `DeltaVarint`）；
* `type` / `strId` / `flag` → `encodeU32Column`（小枚举 → `Dict`/`BitPack`/`Const`）；
* `val1` / `val2` 是 **float 的位模式**当 `u32` 存（逐位无损；`bpmMultiplier` 那种只有几十个取值
  → `Dict`）。

每列前缀 `u64 byteLen`，于是读取方可以跳过不关心的列（`u64` 允许单列 > 4 GB）。

### 3.4 Camera（段 id 9）

`MoveCamera` 事件与砖数无关（一张谱最多几十~几百条），所以**不塞进 16 B 的 `FastAction`**，
用定长记录单独一段。记录 38 B（小端）：

```
floor(i32) | id(u32) | angleOffset(f32) | duration(f32) | x(f32) | y(f32)
| rotation(f32) | zoom(f32) | ease(u8) | relativeTo(u8) | flags(u8) | disabled(u8) | tag(u16 池下标)
```

* `id` 缺失写 `0xFFFFFFFF`（排序时等同 Re_ADOJAS 的 `Infinity`）。
* `flags` 的位是**跨实现契约**（`LevelData::CamFlags`，`static_assert` 钉住）：
  `1 hasPosition / 2 hasX / 4 hasY / 8 hasRotation / 16 hasZoom / 32 inactive / 64 editorOnly / 128 easeWritten`。
  `hasPosition` 与 `hasX/hasY` 是两件事：`position:[null,null]` 时前者置位、后两者不置位
  （docs/camera.md §4.3/§4.4 的 dedup 就靠这个区分）。
* `disabled` 的位：`1 position / 2 rotation / 4 zoom / 8 relativeTo`。
* `relativeTo`：`0 Player / 1 Tile / 2 Global / 3 LastPosition / 4 LastPositionNoRotation /
  0xFE 写了但认不得 / 0xFF 没写`。
* `tag` 走字符串池（与 `strId` 同一张表；**写入方必须在序列化池之前**把这些 tag 加进去）。
* 记录顺序 = 文件顺序（`order` 不入库，读侧按记录下标重排）。

### 3.5 Repeat（段 id 10）

`RepeatEvents` 只服务运镜展开（其它事件暂不消费）。记录 19 B：

```
floor(i32) | repetitions(f32) | interval(f32) | gapLength(f32) | flags(u8) | tag(u16 池下标)
```

`flags`：`bit0 = isBeat（repeatType != Floor）`、`bit1 = executeOnCurrentFloor`。语义见
docs/camera.md §2.3。两段都**只在非空时写**；旧文件没有它们 → 读侧得到空 vector（正确结果：
这张谱没有运镜）。

### 3.8 MoveTrack（段 id 13，v5 起 54 B）

`MoveTrack` 事件，**v5 记录 54 B**（v4 为 52 B，无 `eventTag`）：

`floor(i32) | angleOffset(f32) | durBeats(f32) | gap(i32) | startOff(i32) | endOff(i32) |
 startRel(i8) | endRel(i8) | ease(u8) | flags(u8) |
 offX(f32) | offY(f32) | rotDeg(f32) | scaleX(f32) | scaleY(f32) | opacity(f32) | eventTag(u16 池下标)`

- `flags`：bit0 offX / bit1 offY / bit2 rot / bit3 scale / bit4 opacity / bit5 inactive / bit6 editorOnly。
- `scaleX/Y`、`opacity` 已归一（%/100）；`startRel/endRel`：-1 绝对 / 0 ThisTile / 1 Start / 2 End。
- 触发时间与 durSec 在加载时由 timeline 计算，不存。

### 3.7 Flash（段 id 12，v4）

`Flash` 事件，记录 **32 B**：

`floor(i32) | duration(f32) | angleOffset(f32) | plane(u8) | style(u8) | ease(u8) | pad(u8) |
 startColor(RGBA, 4B) | endColor(RGBA, 4B) | startOpacity(f32) | endOpacity(f32)`

- `plane`：0 = Foreground / 1 = Background；`style`：0 = Flash / 1 = Kill / 2 = StayBlack。
- `startOpacity/endOpacity` 已归一成 0..1。颜色只存 RGB（alpha 由 opacity 决定）。
- 触发时间不存（由 `floor` + `angleOffset` + timeline 在加载时算）。

### 3.6 Colour（段 id 11，2026-10-17 / v4 扩到 50 B）

`ColorTrack`/`RecolorTrack` 与运镜同理：一条事件一个富结构，**不塞进 16 B 的 `FastAction`**。

* **v3 记录 32 B**（只有 ColorTrack 字段）；
* **v4 记录 50 B**：在 32 B 之后追加
  `startOff(u32) | endOff(u32) | startRel(i8) | endRel(i8) | gapLength(u32) | angleOffset(f32)`
  （RecolorTrack 的范围/触发；ColorTrack 事件这些字段为 0）。读侧按文件版本选 32/50，
  v2/v3 仍可读。

32 B 部分：

`floor(i32) | colorType(u16 池) | color(u16 池) | secondary(u16 池) | pulse(u16 池) | style(u16 池) |
 animDuration(f32) | pulseLength(f32) | glowIntensity(f32) | duration(f32) | ease(u8) | flags(u8)`

- 池下标 0 = 空串；读侧把空串还原成 Re_ADOJAS 的硬编码缺省（Single/debb7b/ffffff/None/Standard）。
- `flags` 与 `LevelData::ColorFlags` 同值：bit0 justThisTile / bit1 inactive / bit2 editorOnly /
  bit3 hasGlow（写了 `trackGlowIntensity`；否则用 settings 的值）。
- `order` 不存 —— 它 = 记录下标（文件顺序）。`startFloor` = `floor`，`startTime` = 0（与
  Re_ADOJAS `createShiftType` 一致）。
- 旧读者遇到未知段 id 会跳过（段目录带长度），所以这是向后兼容的追加。

## 4. 列编码（Codec）

列头（20 B）：`codec(u8) | bits(u8) | flags(u16) | count(u64) | aux(u64)`；
`aux` = 字典项数（`Dict` 用），其余编码为 0。

| codec | 值 | 载荷 | 用在 |
|---|---|---|---|
| `Raw` | 0 | 定宽原始（double/int64 8 B，u32 4 B）| 高基数兜底 |
| `Dict` | 1 | `aux × 8 B`（double/int64）或 `aux × 4 B`（u32）字典 + 位打包下标 | 基数小（主编码）|
| `DeltaVarint` | 2 | 首值 zigzag varint，其后 zigzag(相邻差) varint | 单调列（`floor`）|
| `Const` | 3 | 一个值（8 B / 4 B）| 整列同值 |
| `BitPack` | 4 | 位打包（位宽 = `ceil(log2(max+1))`）| 小枚举/位标志 |
| （5 保留）| 5 | — | 曾计划 `JsonPassthrough`，**未实现**；写侧不产出、读侧遇到即失败 |
| `Rle` | 6 | 字典 + `u64 runCount` + 每游程 `(varint 下标, varint 长度)` | 长游程（直线型赫兹谱的 angleData、type/flag/val1/val2）|
| `DeltaRleVarint` | 7 | `u64 runCount` + 每游程 `(varint zigzag(差分), varint 长度)`——游程是对**差分流**取的 | 单调且差分有游程（floor）|
| `SectionZstd` | 16 | 段内容是一整帧 zstd | **段级压缩，v2 默认**（实测真实文件上比 xz 更小、解码更快、零新依赖）|
| `SectionXz` | 17 | 段内容是一整帧 xz | **仅读侧兼容**（旧文件）；writer 只写 SectionZstd |

位打包是**低位在前**、1..32 位/值。`Dict` 的下标与 `Raw/Const` 的载荷都按 `count` 读取，
任何越界/截断都返回 `false`。

## 5. 实测

`adocao pack <谱> <out.adocao> --codec-report` 打印每列的编码、元素数、朴素/编码后字节、
字典项数与位宽。

**MYC（6,770,912 层 / 6,181,981 action）：611.18 MB → 19.58 MB = 3.033 B/层（31×，0 换页）**

| 列 | 编码 | 每值 | 字典 |
|---|---|---|---|
| `angleData` | Dict | 0.7501 B | 52 项 / 6 bit |
| `actions.floor` | DeltaVarint | 1.0000 B | — |
| `actions.type` | Dict | 0.2500 B | 4 项 / 2 bit |
| `actions.strId` | Const | 0.0000 B | 1 项 |
| `actions.flag` | BitPack | 0.1250 B | 1 bit |
| `actions.val1` | Dict | 0.7500 B | 40 项 / 6 bit |
| `actions.val2` | Dict | 0.3750 B | 7 项 / 3 bit |

`angles360`（5,564 层 / 14 action）→ 0.02 MB（3.168 B/层，`angleData` 字典 1,167 项 / 11 bit）。

### 5.1 音频谱（`Song.adofai` 那一类）：primer 只赢 1.10× —— **按停手线停止**

**primer（68,411,077 层 / 68,023,438 action）：7.38 GB JSON → 324.36 MB**（对明文 22.8×），
但**对 `xz -9e` 的 357.12 MB 只有 1.10×** —— 低于本格式的停手线（<1.5× 就停），
所以**不再为这一类继续加专用机制**。逐列一看就明白为什么：

| 列 | 编码 | 每值 | 说明 |
|---|---|---|---|
| `angleData` | **Const** | 0.0000 B | 6,841 万个角度**全部相同** |
| `actions.floor` | DeltaVarint | 1.0000 B | 68 MB |
| `actions.type` / `strId` / `flag` / `val2` | **Const** | 0 | 各列常量（共 96 B）|
| **`actions.val1`** | **Raw** | **4.0000 B** | **272 MB = 全文件的 84%** |

结论与教训：

* 这张谱的**音频数据在 `actions.val1`（每层的音量）**，而不是我早先以为的 `angleData`；
  6,841 万个值几乎互不相同 → 字典不划算（`Dict` 候选算出来比 `Raw` 还大）→ `Raw` 胜出。
  也就是说这 272 MB 是**实打实的 4 B/事件的信息量**，通用手段压不动。
* 早先"从中段采样估计字典基数"的启发式**对它完全无效**：`angleData` 是整列常量，
  任何采样点看到的都是同一个值（这也解释了当时连着两次量出"去重 1"）。
* **向量化的收益边界**：观赏谱（MYC）31×，音频谱 1.10× —— 差别的来源不是"格式好不好"，
  而是**数据本身的基数**。格式已经把能省的都省了（其他六列合计 68 MB，理论上都来自 floor 的差分）。

### 5.2 载荷列的"共享"浪费 + 段级压缩（Twirl 专项，实测）

**问题**：`Actions` 的 6 列是**所有事件共享**的 —— 一条没有载荷的事件（典型是 `Twirl`）仍然要在
`val1`/`val2` 的下标流里占位。MYC 实测：

* actions **99.6% 是 Twirl**（6,155,053 / 6,181,981）；Twirl 的 `val1`/`val2`/`strId` 非零比例**全是 0%**；
* Twirl 现在占 floor 5.87 MB + type 1.47 MB + **val1 4.40 MB + val2 2.20 MB** = 13.94 MB；
* **按类型稀疏化载荷列可省 6.60 MB / 19.58 MB = 33.7%**（val1 4.40 + val2 2.20）。

**改法（保持事件顺序、不改语义）**：`val1`/`val2`/`strId` 改成**按类型稀疏**的列 ——
每列只写"真正使用它的类型"的那些事件，列头加 `u64 usedCount`；读取方按固定的"类型 → 用哪些列"
表，遇到不用的类型就跳过（值取默认 0）。事件顺序完全不变，因此 `processActions` 的语义逐位不变。

**更大的杠杆是段级压缩**（P4）—— 实测 `.adocao` 再 xz -9e：

| 谱 | 明文 | `.adocao` | + xz -9e | 说明 |
|---|---|---|---|---|
| MYC（615 万连续 Twirl）| 611.18 MB | 19.58 MB | **~11 KB** | 极度规则，**不代表一般谱面** |
| The Moon | 15.60 MB | 1.25 MB | **<10 KB** | 同上 |
| angles360（人工合成）| 0.03 MB | 0.02 MB | 0.01 MB | 1167 个角度 → 压不动多少 |
| **primer（音频谱）** | 7.38 GB（xz-JSON 357 MB）| 324.36 MB | **195.43 MB** | **对 xz-JSON 1.83×**，越过停手线 |

**于是修正 §5.1 的停手结论** ✗：pimer 的"只有 1.10×"**只在"不压缩"的前提下成立**；
段级压缩后是 1.83×，**P4 应当提上来做**。注意 MYC/The Moon 的 KB 级结果不可外推
（那是"数据几乎完全可预测"的极端情形）。

**下一步（音频谱）**：`DeltaF32` 列编码（对**数值**相邻差差分再压）。依据：primer 的 `val1`
按**位模式** `Raw` 存（324 MB）时，仅 xz 就能到 195 MB（1.66×）→ 说明那些 float 里有真实结构，
而位模式表示把它丢掉了。**先实测数值差分后的熵再决定**。

### 5.3 赫兹谱（audio-as-chart）的"隐式"编码能省多少（实测）

用户指出"它的地图基本上全是直线" —— 这正是赫兹谱的签名：**角度就是采样值**，被量化到一个很小的
调色板。实测 MYC（6,770,912 层 / 6,181,981 action）：

* 调色板 **52 项**，前 4 名合计约 **80%**；**严格轴对齐（90° 的整数倍）占 47.1%**，其余多为 45° 系列
  → 在整图尺度上"斜线也是直线"，所以视觉印象与数据一致；
* "**每层一条 Twirl 且 floor 连续**"覆盖 **90.42%**（5,589,469 / 6,181,981）；例外只有 **592,512** 条
  （其中 565,584 条是"该层没有 Twirl"的缝隙，另有 PositionTrack 26,480 / SetSpeed 315 / Bookmark 133）；
* 于是这一族最省的形状是：角度调色板下标 **4.84 MB** + Twirl **位图 847 KB**（位图天然表达那 9.6%
  的缝隙）+ 非 Twirl 事件显式 **~0.2 MB** ≈ **5.9 MB**（现在是 19.58 MB，**−70%**），再 xz 就是 KB 级。

**风险与兜底**：位图化会改变"同一层里 Twirl 与其它事件"的原始交错顺序 → 顺序定义（例如"同层 Twirl
先于显式事件"）必须与 `processActions` 的语义一致，并由 `archiveRoundTrip` 的 **13 节逐位比对**兜住。
换句话说：这条优化是**可安全尝试**的，因为一旦顺序错了，逐位比对立刻会红。

**外推的边界**：以上是"赫兹谱 + 极规则"这一族的结果。手工谱请以 `angles360`（1,167 个角度、
几乎压不动）为参照，不要拿 MYC 的 KB 级去预期。

### 5.4 游程（RLE）在哪些列上真的有用（实测，含一个反直觉结果）

用户给了四张赫兹谱的实拍图：竖直**锯齿** / 45° **长直线** / 水平线 + **整圈**砖 / **L 形**拐角。
它们对应"相对角"列的三种结构：**同值长游程**（直线 / 整圈）、**短周期交替**（锯齿）、
**两段长游程拼接**（L 形）。实测各列的游程（MYC / The Moon）：

| 列 | 游程均值（MYC / The Moon）| 结论 |
|---|---|---|
| `angleData` | **1.0 / 1.1** | **RLE 反而更差**（5.08 MB → 11.58 MB）—— MYC 是锯齿型（音频速率 ±90 交替）|
| `type` | 117 / 15.4 | RLE 极佳（MYC 1.55 MB → 66 KB，23×）|
| `flag` | 11,179 / 1,023 | RLE 极佳（773 KB → 839 B，920×）|
| `val1` | 118 / 15.4 | RLE 极佳（4.64 MB → 92 KB，50×）|
| `val2` | 62,444 / 2,434 | RLE 极佳（2.32 MB → 166 B，14,000×）|
| `strId` | 全列一个值 | 已经是 `Const`（24 B）|
| `floor` | 差分后游程均值 1.0 | 需要"**对差分流再取游程**"：6.18 MB → 十几字节 |

**要点**：地图上的"直线"= **相对角恒定** = `angleData` 的**长游程**；但 MYC 恰好是**锯齿**那一型
（游程均值 1.0），所以 RLE 对它的角度列无用。也就是说**同族内也分两型**（直线型 / 锯齿型），
而"每列算出候选再取最小"的设计**两种都能自动选对**，不需要按谱面类型分派。

**要做的事**：加一个 `Rle` 列编码（值 + 游程长度 varint），并给单调列加
`DeltaRleVarint`（先差分再对差分取游程）。判据必须是"**实测字节数最小**"，
而不是按列名/类型硬编码 —— 否则直线型和锯齿型总有一边会选错。

### 5.5 这类谱的真实信息量：单元 × positionTrack 摆放（实测）

用户指出这类谱"都是拿这些单元拼起来的，成千上万个拿 positionTrack 排列"。实测 MYC 证实：

| 度量 | 实测 |
|---|---|
| 周期 8 的"单元"种类 | 846,363 个窗口里只有 **568 种**，**前 4 种占 75.7%** |
| 周期 2 的"单元" | **223 种**，最常见一种占 24.2%，前 4 种占 72.8% |
| `PositionTrack` | **26,480 条**；x 只有 **19 个不同值**、y 只有 **7 个**（x∈[-9,15]、y∈[-8.7,2]）= 小网格 |
| 摆放数据本身 | **0.20 MB**（26,480 × 8 B）；按"19×7 网格调色板"存约 **26 KB** |

**结论**：这类谱的真实信息量只有**几百 KB** —— 它本质是一段程序："在网格 (x,y) 上放第 U 号单元"，
重复 26,480 次；角度流是从几百个 motif 里挑的。其余全是生成出来的。

**对编码的含义**：
1. `PositionTrack` 的 val1/val2 天然落进 `Dict`（19 / 7 个取值 → 5 + 3 bit）—— 已有编码就够了；
2. 角度流需要**比 RLE 更贴形状**的候选：`Motif`（周期 p + motif 字典 + motif 下标流）。
   注意 RLE 对这种"短周期交替"无能为力（游程均值 1.0），而 `Motif` 正是为它准备的；
3. **判据仍然是"实测字节数最小"**：`Dict`/`Rle`/`Motif`/`Raw` 四个候选一起算，谁小用谁 ——
   直线型谱会在 angleData 上选 RLE，锯齿/单元型会选 Motif，人工谱会选 Dict 或 Raw。

**不手搓 motif 也可以**：xz 已经能吃到这类长程重复（实测 19.58 MB → ~11 KB）。
但 `Motif` 的价值在于**不依赖"完全可预测"**：真实的赫兹谱若 motif 顺序半随机，xz 可能只有 2~4×，
而 motif 编码能到 ~10~20×。所以两者都留着（段级压缩 + motif 候选），谁小用谁。

### 5.6 三个版本的对比：xz 已经吃下这一族，Motif 暂缓（实测）

同一张谱的三个版本（MYC / v300 = 同谱的"瘦 actions"版 / v282 = no three planets）：

| 谱 | 层数 | 调色板 | angleData 列 | **xz(角度下标流)** | 占比 | p=8 单元 | p=2 单元 | PT | PT_x | PT_y |
|---|---|---|---|---|---|---|---|---|---|---|
| MYC | 6,770,912 | 52 | 5,078,620 B | **3,652 B** | **0.1%** | 568 | 223 | 26,480 | 19 | 7 |
| v300 | 6,770,912 | 52 | **与 MYC 逐字节同长** | **3,652 B** | 0.1% | 568 | 223 | 26,480 | 19 | 7 |
| v282 | 6,377,688 | 52 | 4,783,702 B | **3,600 B** | 0.1% | 569 | 221 | 26,480 | 19 | 7 |

**结论**：
1. 这一族的重复性**完全落在 xz 的能力范围内**（角度流 0.1%）→ 专门写 `Motif` 编码**不值得**
   （那会是一个更差的 xz 复制品）。§5.5 里提的 Motif 因此**暂缓**。
   **可测的复活条件**：若某张谱的角度列 xz 后占比 **> 10%**（即 xz 吃不下），再回来做 Motif。
2. **JSON 的啰嗦程度不影响 `.adocao`**：v300（300.9 MB JSON）与 MYC（611 MB JSON）压出来几乎一样大
   （19.26 / 19.58 MB）—— 因为二进制存的是**解析后的结构**（16 B/action），
   JSON 层的字段名冗余被彻底消掉了。
3. 因此实现顺序（按实测收益）：**段级 xz（P4）** → 便宜的列级优化（`Rle`、稀疏载荷列、
   `PositionTrack` 走 `Dict`）→ `Motif` 只在触发条件满足时再做。

### 5.7 到底是 LZMA2 的哪一部分在干活（参数扫描 + 打乱对照）

对象：MYC 的角度下标流单独导出（5,078,184 B = 6,770,912 个 6-bit 下标，字典 52 项）。

**对照实验（只改"顺序结构"）**：

| 变体 | xz -9e |
|---|---|
| 原始 | **3,148 B**（0.062%）|
| 4 KiB 块内打乱（毁长程、留局部）| 2,170,989 B（42.8%）|
| 全局打乱（直方图不变、重复全毁）| 2,756,954 B（54.3%）|
| 纯直方图熵下界（52 符号，4.21 bit/字节）| ≈ 2,612 KB |

→ **相差约 880×**：靠"符号分布偏斜"几乎不省（下界本来就 2.6 MB），**省下来的全部来自顺序结构**。

**参数扫描（只改一个 LZMA2/LZMA1 参数）**：

| 变体 | 输出 | 相对基线 |
|---|---|---|
| `preset=9e`（基线）| 3,148 B | — |
| `nice=8`（匹配最长只找 8）| 4,004 B | **+27%** |
| `lc=0,lp=0,pb=0`（关掉字面量上下文）| 3,088 B | **−2%**（完全无关）|
| `preset=1`（1 MiB 字典 / hc4）| 3,965 B | +26% |
| `dict=4KiB`（字典只留 4 KiB）| 4,634 B | **+47%** |
| `depth=4`（搜索只找 4 步）| 3,269 B | +4% |
| LZMA1 vs LZMA2（容器开销）| 3,127 vs 3,148 B | 21 B |

**结论**：**LZMA2 这一层没有贡献**（只多 21 B）；干活的是里面的 **LZMA1 LZ77 匹配编码器**，具体是
（a）**`rep0`~`rep3` 重复距离**（周期 motif 几乎免费的原因）＋（b）**可达距离超过 4 KiB 的匹配**
（重复是长程的）＋（c）**很多短匹配**（不是"一个超大周期"）。字面量上下文模型、匹配搜索深度、
LZMA2 分块/状态重置全都无关。这也解释了为什么**不需要写 `Motif` 编码**：
**LZ77 的 rep-match 本来就是一个自适应单元字典**，而且自动适配"单元在哪里重复"。

**对 P4 的实际结论**：
1. 字典留大（≥64 KiB，即 `preset=9e` 档）；
2. 按列分段压缩安全（单列重复距离只有几十 KiB，自己一段更密）；
3. **不要为字面量模型做字节整形**（转置/字节平面拆分无效）；
4. 可以用快预设（`preset=1` 也只要 3,965 B，对 0.062% 的基线而言 +26% 无意义）→ 解码更快。

### 5.8 换算法家族看分工，以及 P4 该选哪个压缩器（实测）

同一份 MYC 角度下标流（5,078,184 B）喂给不同家族的压缩器：

| 算法 | 输出 | 占比 |
|---|---|---|
| gzip -9（LZ77 + **Huffman**）| 14,341 B | 0.282% |
| zstd -19（LZ77 + FSE/Huffman）| **3,438 B** | 0.068% |
| xz -0（LZ77 + 算术编码，256 KiB 字典）| 4,740 B | 0.093% |
| xz -9e（+ rep 距离 + 64 MiB 字典）| **3,212 B** | 0.063% |
| bzip2 -9（**BWT，不是 LZ77**）| 4,563 B | 0.090% |
| *（对照）* xz -9e / gzip -9 打在**全局打乱**的同一份数据上 | 2,757,024 / 3,072,148 B | ~55% |

**分工**：
1. **匹配器扛绝大部分**：5 MB → gzip 的 14 KB ≈ **354×**（LZ77 找重复这一步）；
2. **算术编码再补 ~4.5×**：同样的匹配，Huffman 只能到 14 KB，算术编码到 3.2 KB；
   `rep` 距离 + 大字典再补 ~1.5×（xz -0 → -9e）；
3. **但不是 LZ77 独家**：bzip2（BWT）也到 4.5 KB —— 这份数据重复得太强，"谁来都能找到"。
   准确说法：LZ77 是"发现单元"的一半，算术编码是"把 token 压到亚比特"的一半，缺一不可。

**P4 该选谁（结论）**：**用 zstd** ——
* 体积几乎持平（zstd -19 = 3,438 B vs xz -9e = 3,212 B，**只差 7%**）；
* 解码快得多（对"打开谱面"这条路径更值）；
* **零新依赖**：`adocao_archive` 本来就链着 `libzstd_static`（见 AGENTS）。
* xz 保留为可选高档（体积敏感时用）。

### 5.9 成绩单：Won't You 现在能压到多少（实测）

| 谱 | 明文 JSON | `.adocao`（**已实现**）| + `zstd -19` | + `xz -9e` | 结构优化投影 + 压缩 |
|---|---|---|---|---|---|
| **MYC** | 611.18 MB | **20,534,344 B（19.58 MB）** | **9,795 B** | 10,012 B | **5,838 B** |
| v300 | 300.9 MB | 20,534,352 B（19.58 MB）| 9,798 B | 10,040 B | 5,847 B |
| v282 | 282.2 MB | 19,256,384 B（18.36 MB）| 9,539 B | 9,804 B | 5,776 B |

三条结论：

1. **现在（P1 已实现）就能到 19.58 MB** —— 611 MB → 19.58 MB（31×），已经可传播。
2. **只加 P4 就到 ~9.6 KB**（611 MB → 9,795 B ≈ **6.2 万倍**）。注意在这个**真实文件**上
   `zstd -19`（9,795 B）**比 `xz -9e`（10,012 B）更小** —— 与"裸下标流上 xz 略胜"的结论相反，
   所以 §5.8 选 zstd 是对的（零新依赖 + 解码更快 + 文件上更小）。
3. **再做 RLE + 稀疏载荷列**：未压缩 19.58 MB → **9.23 MB**（−53%），压缩后 9,795 → **5,838 B**
   （再省 **40%**）→ 结构优化并没有被压缩器吃掉，仍然值得做。
   （投影是**保守**的：角度列按 1 B/值算，实际位打包后是 6 bit。）

参考（另一族）：primer（音频谱）324.36 MB → 压缩后约 195 MB —— 那一族的大头是 `actions.val1`
里近乎随机的 float，属于 §5.1 的范畴（`DeltaF32` 是它的下一步）。

## 8. v3 设计（提案 —— **尚未实现**）

> ⚠️ 本节是设计草案，**不是现状**。当前实现是 v2（§2–§4）：8 个列 codec + 段级 zstd + 稀疏载荷列，
> **double 列连一个差分候选都没有**。本节所有收益数字都是**合成实测**（除非另标），目的是定结构、
> 不是承诺比例 —— 真谱比例要按 §8.4 的判据实测后再定。

### 8.0 三条不变量（v3 不许破）

1. **逐位无损**：编完必须解回来逐元素 `memcmp`，任何一位不一致 → **丢弃该候选**、退回 `Raw`
   （`AdocaoColumns.cpp:279-297` 已有；无损容器里没有"近似"这一档）。
2. **最小由实测决定**：每列/每块把候选**真编一遍**取最小；`Raw` 永远在候选集里 ——
   于是**加任何候选的最坏情况是零收益，不会让任何谱变差**。
3. **变换必须精确可逆**：只在整数 / 定点 / 位模式域做；**浮点域的预测一律不许进**（理由见 §8.2）。

### 8.1 编码 = 变换 × 后端（v3 的核心结构改动）

v2 是"一列选一个 codec"；v3 拆成两层，候选空间 7 → 5 变换 × 7 后端（`Varint`/`RleVarint`/`Dict`/`BitPack`/`Const`/`Raw`/`Motif`）：

| 变换（可叠、可逆、逐位精确） | 抓什么结构 | 实测（合成，1.7M 值列） |
|---|---|---|
| **`WrapDelta(mod 360)`**（一阶/二阶） | **环上的量**：行进方向 —— 螺旋/圆周/大滑音 | 13.60 MB → **0.62 MB（22×）**；转向率抖动 0.5%/5% → 4.24 / 8.28 MB |
| `Delta` / `Delta2` | 单调、缓变（漂移、时间戳） | "漂移+周期毛刺" 0.21 MB vs `Dict` 18.06（**86×**） |
| `Predict(k)`（低阶线性预测） | 少数谐波（傅里叶 / epicycle 型） | 与 `Motif` 同量级；残差必须走 §8.2 |
| `FixedPoint`（网格判定 + 整数化） | 二进制网格 `k·2^e` | 100×+（**十进制量化已被 `Dict` 免费吃掉 2×**） |
| `XorFloat`（前值 XOR + 前导零） | 全精度平滑漂移（无网格） | ~1.9×（对随机数据 **0 收益**） |

⚠️ **哨兵必须先掩码 —— 否则 `WrapDelta` 与 §8.4 的判据一起被毒化。** `angleData` 列里**混着 `999`**
（midspin；`LevelData.cpp:1427-1430`，`1509` 的 `!` 也解析成 999），而 `AdocaoWriter.cpp:148` 是把它
**原样**当 double 列写的。于是 `999 mod 360 = 279` 成了**假角度**，999↔真角度的相邻对又制造一大批
**假的 `|Δ| > 180`** —— 正好把"环绕率"这个判据指向"该上 `WrapDelta`"。
→ 规则：`WrapDelta`（及任何 mod / 差分变换）**只作用在掩码后的真角度流上**；哨兵另存
（`BitPack`/`Rle` 的 1 bit 位图，或 999 归一成 0 再单开一列）。`Dict`/`Raw` 不受影响（逐位原样）。

| 后端 | 载荷 | 备注 |
|---|---|---|
| **`Varint`（新增）** | zigzag varint，**不对流做差分** | 残差 / 已差分流的默认后端（§8.2④）|
| **`RleVarint`（新增）** | zigzag varint + 游程，**不做差分** | 残差自身有游程时 —— v2 `DeltaRleVarint` 去掉差分那一半 |
| `Dict` / `BitPack` / `Const` / `Raw` | 见 §4，格式不变 | `Raw` 永远在候选集里（§8.0-2）|
| **`Motif`（新增）** | 周期 p + motif 字典 + 下标流 | 抓周期/谐波/单元重复 |
| ~~`DeltaVarint` / `DeltaRleVarint`~~（v2） | **自带差分** → 在新结构里等价于"`Delta` 变换 + `Varint`/`RleVarint` 后端"的**融合体** | 冻结保留（读侧兼容），v3 新候选一律走正交结构 |

⚠️ **"正交"是要显式做出来的，v2 的整数后端不正交**：`AdocaoColumns.cpp:383` 的 `DeltaVarint` 写的是
`zigzag(v[i]−v[i−1])` —— **它自己会再差一次**，`DeltaRleVarint` 同理。而变换（`WrapDelta`/`Delta2`/`Predict`）
**已经产出差分/残差流**，直接喂给它们会变成二阶/三阶差分、语义错位。所以 §8.2④ 里的"zigzag varint"
**必须**是上面新增的 `Varint`/`RleVarint`，**不是**复用 v2 那两个。

**`Motif` 实测**（三条谐波列）：单谐波 f=1/2000 → **0.08 MB**、f=1/100 → **0.06 MB**、
六谐波 epicycle → **0.18 MB**（对 `Raw` 13.60 MB 是 **75~220×**），p=32 时窗口唯一数只有 125/64/478。
⚠️ 前提是"周期能被窗口捕捉"：**频率为无理比时窗口集不重复、`Motif` 会失效** → 那时由残差编码兜（§8.2）。

### 8.2 预测误差（残差）怎么处理 —— 无损的关口

**① 预测只在整数域做。** 先判定整列落在精确网格（`v·2^e ∈ ℤ` 或 `v·10^e ∈ ℤ`），转 `int64` 再差分/预测，
残差是**精确整数**，"误差"根本不出现。浮点域不行：`residual = v - pred` 是一次正确舍入的减法，
但 `pred + residual` **未必等于 v** → 误差会**永久漂移**。

**② 环绕也必须在整数域。** `360.0` 本身精确，但 `v mod 360` 对网格值不保持网格 ——
做法是缩放到整数 `k`、取模数 `W = 360·S`（`S` 为整数 scale；合成实测用 `S = 10^6`）。

**③ 闭链 + 每块复位。** 预测要从**解码端会看到的（重建）值**算；整数域里开链与闭链等价
（现有 `DeltaVarint` 写的就是 `v[i] - v[i-1]`，安全），一旦引入浮点就不再等价。
且预测链必须能重启：**块边界（同时是 checkpoint 边界）= 复位点**，每块自带首值/初始状态。

**④ 残差的后端**（这是"误差处理"的实体，直接复用 §4）：

| 残差形态 | 后端 |
|---|---|
| 集中在 0 附近 | **`Varint`（新增，不做差分 —— §8.1 的坑）**；1 字节覆盖 \|r\| < 64 |
| 取值少（如螺旋残差只有 5 种） | `Dict` |
| 有游程 | `Rle` / **`RleVarint`（新增，不做差分）** |
| 有界（如 \|r\| ≤ 3） | `BitPack`（3 bit/值 —— 螺旋 622 KB 的地板就是这个）|
| 残差自身仍有周期 | `Motif`（在残差上做窗口字典）|
| 高熵（预测失败） | `Raw` → 整个候选输给 `Raw`、被丢弃 |

最后整段过 `zstd`（§4）。

**⑤ 溢出与自检。** `int64` 差分的极值是有符号溢出（UB，按 #0 的规矩显式判）；
**定点缩放本身也会溢出** —— 转 `int64` 之前就要判幅值（`|v| > INT64_MAX / S` 直接放弃该候选），
环绕取模同理（`W = 360·S` 必须能放进 `int64`，且 `v·S` 的中间量不许溢出）；
自检（§8.0-1）是最后一道 —— 失败即丢候选，**不是**"误差可容忍"。

**反例（"在错误的域里预测"长什么样）**：朴素 `Δ²` 直接作用在 double 上 →
残差 **16.9~20.4 MB，比 `Raw`（13.60）还大**：double 差分带舍入噪声 → 残差成高熵、游程≈n、varint 每个 3~4 B。

### 8.3 分块（一次解决"分段型压得更好"与"可按层号 seek"）

* 块头：`firstIndex` + **块自包含**（首值绝对值 / 初始状态）；**块内各自选变换与编码**。
* 块大小与 checkpoint 间隔**对齐**（4096 层），渲染侧的分块建议复用同一批边界。
* 实测（"不规则 f + 平滑"拼接列）：全局一码 → 按 4096 分块，**f=5%/20%/40% 省 3.29× / 2.09× / 1.66×**；
  块的类型分布精确圈出混乱位置（5% 混乱 = 20 个 `Raw` 块）。
* ⚠️ 分块只对**分段型**有效；**叠加型**（网格摆放 × 单元）要靠**按列/按事件类型分解**，切块切不开它。
* ⚠️ **块大小要按列定，不能全局一个数（上面那组实测没覆盖字典主导列）**：`Dict` 才是现在的主力编码
  （MYC 族、§5.5 叠加型），而"块自包含"意味着**字典也按块重开** → 字典主导的列在小块下会重复付
  字典费、体积**可能变大**。两条出路（可并存，按实编取最小）：① 每列/每事件类型**各自**挑块大小；
  ② **字典段跨块共享 + 下标流按块**。判据进 §8.4（**块间字典复用率** + 分块前后体积比），
  否则看不出是赚是亏。
* ⚠️ **"压缩帧大小"与"seek 粒度"要解耦**：2.1e9 层按 4096 切 = **512,695 块**；每列每块一帧 zstd 的话，
  光帧头就 ≈ 512,695 × 列数 × ~13 B（~10 列 → **65 MB**），且 32 KB 帧的压缩率明显低于大帧。
  → 压缩帧开 **64 KB ~ 1 MB**（16~256 个 checkpoint），seek = **定位所属帧**再解码到目标块；
  checkpoint 粒度仍保持 4096（渲染窗口要的是它，不是帧）。

| 一阶 / 二阶差分后的基数（raw 与 wrapped 各一份） | 小 → `Delta`/`Delta2` → `Dict`/`Rle` | 只作参考 —— 见下一行 |

| 自相关主峰 + **p-窗口唯一数** | 有主峰 + 唯一数塌陷 → `Motif` | 窗口按**位模式**哈希。⚠️ 前提是**逐位重复**：同一个大七和弦波形，全精度（每层差 1 ULP）的窗口唯一数 = 窗口总数、一个都不重复；量化到 1e-6 后就塌到 **120/16265@p120**。裁决里**必须把窗口字典本体算进去**（`唯一数 × p × 8 B`）|
| 定点网格判定 | 成立 → `FixedPoint` | 两条硬口径：① **2^e 上限 20**（任何 double 都落在某个 2^-N 上，不设限则每列都"落在网格上"，1.2× 的小便宜会挤掉真结构）；② 十进制**精确判定** `k/10^e == v`，**不许用容差**（容差会把均匀随机谱误判成 10^-9 网格）|
| 游程数 | 多 → `Rle` | v2 的 Rle = 字典 + (下标, 游程长度) 对，估算按这个形状算（实测 diag_dict 7434 B vs 真编 7462 B）|
| **空间自重叠率**（1 砖格子，落进已占用格子的比例）| 高 → 空间被反复访问 | ⚠️ **不等于"叠加型"**：绕圈的滑音实测 **0.9996**（半径 ~0.6 砖的圆来回踩）。要区分得再看**位置序列的周期**，所以报告里只陈述事实、不下结论 |
| **块间字典复用率** + 分块前后体积比 | 复用率降 → 块太大、或该跨块共享字典（§8.3）| 待分块（⑥）落地后才有 |
| 哨兵占比 / 哨兵游程数（`angleData == 999`） | >0 → 环绕率/`WrapDelta` **只能**在掩码后的流上算（§8.1）| 掩码是**纯掩码**（原样拷贝、逐位不动；`maskSentinels` 有专门用例）|

三项都大 → `Raw + zstd`（真没结构，别再挣扎）。

**判据是"未计段级 zstd"的裸估算** —— 报告里显式写了这句。它只用来指方向，权威永远是实编（§8.0-2）。
抽样核对（2026-10-11，七张诊断谱 + MYC 6.77M 层）：`actions.floor` → `DeltaVarint`、
`type`/`val1`/`val2`/`flag` → `Dict`、`strId` → `Const`，与实编一致 ✓；

**规模与 BPM 是"能不能听"决定的，不是随手填的**（两次踩坑换来的）：

* 这些谱**没有音频文件**，播放器于是走"把整谱的打拍音**预混成一段 PCM**"那条路
  （`HitsoundManager::preSynthesize`），缓冲区大小**正比于总时长**。
  曾经 16384 层 @120 BPM = 8192 s → 抓帧探针实测峰值 RSS **2.26 GB**，而且要算完那一大段才出声。
* 于是把整谱压到 ~120 s —— 但 16384 砖 / 120 s = **137 下/秒**，听感是一堵**蚊子声音墙**
  （音高就是重复频率 ≈137 Hz）。**"总时长要短"和"每下听得清"在固定砖数下不能都要**：
  每砖 0.2 s 才有乐音感，16384 砖 x 0.2 s = 55 分钟、预混 1.1 GB。
* 结论：**减砖数**。现在单结构谱 **1024 砖**（叠加 512，分段 2048）、生成器按目标时长反推 BPM
  （`BPM = 层数 × 60 / seconds`，默认 180 s；`--seconds` / `--bpm` 可调），
  实测 `totalDuration` **100~194 s**、峰值 RSS **222 MB**（含 GL 上下文）、每砖 ~0.18 s
  （每秒 3~6 下，**每一下都分得开**）。
* 1024 砖仍然够诊断：周期检测最大 p=120 时窗口有 905 个、塌 7.5 倍（阈值 4 倍）。
  要做 v3 的分块（⑥，4096 一层块）时**另外生成长谱**（同一个脚本，改 `N`/`N_MIXED` 即可）。
* ⚠️ "层数 × 60/BPM"只是**估算**：每砖时长 = `rotation × 2 × 60/BPM`（`Timeline.cpp:82/164`），
  转 90° 只要半拍、方向不变要两拍 —— 实际时长按角度分布浮动（`diag_overlay` 全 90°，
  比估算短一半）。改完用 `adocao_tl_full_dump <谱>` 第一行核对真实 `totalDuration`。

**踩过的坑（都在自测的负向对照里钉住了）**：

1. **浮点域的 Δ² 会骗人**：4 位小数的滑音，真曲率 ~1e-7 被 ±1e-4 的舍入噪声淹没 → 浮点域
   "基数只塌 2.7×"，看着像没结构。**换整数域立刻现形**（3.29 → 1.00 B/值）。所以 §8.2① 那条
   "残差只在整数域算"不是洁癖，是**判据能不能看见收益**的前提。
2. **"任何 double 都落在某个 2^-N 上"**：均匀随机谱的值是 `k/2^29`，于是被判成"落在网格上"→
   `FixedPoint` 赢了裁决。② 的上限（2^-20）和③的精确十进制判定都是为此加的。
3. **`Motif` 要逐位重复**：同一个（大七和弦）波形，量化到 1e-6 就塌成 120 个窗口，不量化则一个都不重复。
   真实谱面里"滑音/谐波"多半是脚本算完**打印**出来的（量化过的），所以这条通常成立 ——
   但**不许假设**它成立。
4. **采样只能取前缀**：环绕率/差分基数全建立在相邻对上，跨步抽样会把相邻对打散。
5. **`p-窗口唯一数` 的最优 lag 会被 p=2 抢走**：周期 96 的数据在 p=2 上同样只有 96 个不同窗口
   （唯一数相同、窗口总数多 94 个）。裁定改为**自相关主峰优先**，只有"唯一数占比低 20% 以上"
   才允许顶掉它。
6. **`spatialOverlap` 的高值不等于叠加型**：`diag_glide` 那种绕圈滑音也是 0.9996。

### 8.8 `Derived` 段：checkpoint（窗口化的断点）—— ✅ 实现见 §8.12

**★ 优先项：PositionTrack 的累积量快照。** 理由：**基础位置**只是 `angleData` 的前缀和（纯函数，
窗口内可从断点续算）；而 `cumX/cumY` 是**事件驱动状态** —— 从第 i0 层续算要么扫遍 `floor < i0`
的全部事件（O(层数)），要么就有快照。它是唯一"不能只靠窗口内数据算出来"的东西。

现有语义（`applyPositionTrackOffsets`，逐行核过）：**全部继承、永不重置** ——

```cpp
for (i = 0..n) { while (event at floor i) { cumX += offX; cumY += offY; } tiles[i].position += (cumX, cumY); }
```

快照字段草案（把同族的继承状态一次收齐，别回头改格式）：

| 字段 | 类型 | 为什么必须在 |
|---|---|---|
| `cumX, cumY` | f64×2 | **PositionTrack 累积偏移（★）**；Hold / `distanceMultiplier` 将来同族 |
| `baseX, baseY` | f64×2 | `angleData` 前缀和（想要 O(1) seek 而不重算窗口起点）|
| `radiusScale` | **f64** | **ScaleRadius 是继承的、且改变步长**（`val4 += dir * ((1−radiusScale)·tileSize)`）|
| `lastAngleDeg` | **f64** | 最后一个**真** `angleData` 原值（0..360；哨兵 `999` 另行标注）—— midspin（999 = 上一层 + 180）要它。**不存"累积方向"**：那会无界增长 |
| `bpm` | **f64** | SetSpeed 继承（Timeline）|
| `timeSec` | f64 | `tileStartTimes` 时间前缀和 |
| `flags` | u32 | 哪些分量有效（稀疏）|

约 **88 B / 4096 层 = 0.021 B/层** → 2.1e9 层 = **45 MB**（占 6.05 B/层 预算的 0.35%）。

⚠️ **快照字段一律 f64，不许出现 f32**（这里先踩过一次设计坑）：`radiusScale` 是**会改变步长的继承量**，
f32 的相对误差 ~6e-8 会在 4096 层窗口里累积成 ≈**2.5e-4 砖**；`bpm` 同理把 `timeSec` 推离真值。
子像素归子像素，但它**过不了 §8.10⑥ 的 `memcmp`** —— 而"从快照重算 = 全谱一次算"正是 checkpoint 的
唯一验收手段（也是全局规矩"timing/position 一律 double"的直接推论）。多 12 MB 不值得省这 3 个字段。

**三条不变量**（不遵守就会重犯别人的 bug）：

1. **快照语义 = "`floor < i0` 的事件全部处理完"之后的状态**（闭包语义）；
2. **窗口重算必须从快照重新生成 position，绝不原地累加** —— Re_ADOJAS `5a5f5b7` 就是
   "`applyRadiusScaleOffsets` 在没有 `copyTo` 的情况下又跑了一遍"，探针期望 `base+[5,3]`、实际 `base+[9,3]`；
3. **窗口的事件扫描必须包含 `floor == i0` 的事件**（若将来实现"单层事件"）。

**前置语义已定：`justThisTile` = 只作用于本层（点加）**。三份来源一致（2026-10-11 定案）：

| 证据 | 说法 |
|---|---|
| 编辑器指南（adofaieditor.gitbook.io → Position Track → "Only change this tile"）| "If enabled, all settings from this event will only affect the event tile" → **点加** |
| Re_ADOJAS 移植（`PositionTrackManager.ts`）| `justThisTile` → `pointX[floor] += …`；非 justThisTile 才 `bitAdd`（后缀加）→ **点加** |
| The Moon 那段的渲染（量出来的）| 花瓣环离星心 **1.5~2.2 倍星半径**；点加模型预测中位 **1.46** / 最大 **2.28** ✓；"一律累积"会把花瓣甩到 **3~5 倍**外 ✗ |

**实现**（`applyPositionTrackOffsets()`）：`Enabled`（= `"Enabled"`/`"true"`/1）只把偏移加到本层；
缺省 / `"Disabled"` 才累进 `cumX/cumY`、作用于本层及之后所有层。回归用例 `tests/position_offset_test.cpp`
（Enabled +[3,0] 在 floor 2 → floor 3 必须回到基础位置；Disabled +[0,2] 在 floor 4 → 一直继承到末尾 extra 砖）。

**过程中的教训（别再犯）**：我一度按"眼看上去哪张图更像"下了"累积"的结论，并把 Re_ADOJAS 判为错；
后来把**尺度无关的量**（花瓣环半径 ÷ 星半径）量出来才定案。**结论必须落在可量的量上，别用"像不像"**。
另外：**不要与 `scripts/capture-gate.sh` 并发跑抓帧** —— 两者共用 `build/ADOCAO.log`，门槛核对 `capture:` 行时
会被另一次抓帧污染，报出一整片假的"不一致"（那次 22/51，单独重跑就是 51/51）。

**对快照的结论**：点加 = 一次性效果，**不跨块边界** → 快照不需要额外字段（不必存"边界上有没有未完成的一次性事件"），
但**不变量 3（窗口/块的事件扫描必须含 `floor == i0`）是必需的**，否则边界那一层的点加会丢。
继承状态（`cumX/cumY`、将来的 `curScale/curRot/curOpacity/curStick`）进快照，由不变量 1 负责。

**与分块同界**：checkpoint 间隔 = 分块间隔 = 4096 层 → "数据块 = 窗口 = checkpoint" 三者同界。

### 8.9 版本与兼容

* `version = 3` 仍是**唯一的兼容闸门**；v1/v2 的双读路径保留（读旧文件行为不变）。

| 4 | `Predict(k)` + 残差后端（§8.2） | 同上 |
| 5 | `FixedPoint` / `XorFloat` | 同上 |
| 6 | 分块（块自包含 + 块内自选；块大小按列定 §8.3） | 格式 v3；读侧双读 —— ✅ **已完成**（§8.11；`archive/AdocaoBlocked.*`）|
| 7 | `Preserved` / `Derived`（先 PositionTrack 快照）| 格式 v3 —— ❌ **待做**（⑧）|
| 8 | `min(zstd, xz)`、零拷贝 | 无 |

**每一步的验收**：① 候选逐一实编取最小 + `Raw` 兜底 + **逐位回代自检**（§8.0）；
② **负向对照**：拿白噪声列证明新候选不会赢、也不会比 `Raw` 大；
③ `.adocao` 与 JSON 两条路出图**逐字节相同**（MYC 677 万层验过）；
④ 像素门槛 **51/51 逐字节相同**；⑤ 地板护栏：MYC 族 ≤ 5,838 B；
⑥ checkpoint 落地时另加**逐位对拍**：对若干 `i0`（含 `0 / 4095 / 4096`、每个 PositionTrack 事件的 ±1、
midspin 跨边界）从快照重算 `[i0,i1]`，与全谱一次算的 `position`/`direction` 做 `memcmp`
（**快照种子一律 f64，见 §8.8** —— 存 f32 这条必然红）；
⑦ **负向对照**：在**含哨兵** `999` 的 `angleData` 列上，未掩码的 `WrapDelta` 候选必须**输给**掩码版
（证明掩码真的在生效，而不是"看起来没坏"）；同样，`DeltaVarint` 直接吃已差分流时必须**输给** `Varint`
（证明 §8.1 那个"不正交"的坑被挡住了）。

## 8.11 v3 分块列容器（⑥ —— ✅ 已实现 2026-10-15）

> 实现：`archive/AdocaoBlocked.{hpp,cpp}`（编码/解码/按块随机访问）+ `AdocaoWriter` 的段级选型。
> 自测：`tests/adocao_blocked_test.cpp`（ctest `adocao_blocked`）。`version = 3` 起写入，
> 读侧**双读 v2/v3**（`kMinReadVersion = 2`）。

### 布局

```
u8 kind | u8 layout | u16 reserved | u64 totalElements
layout == Single (0):                       # 整列一块；"分块没赚到"时的兜底形状
    u8 codec(0=Raw,16=Zstd) | u8[3] | u64 rawSize | u64 storedSize | <storedSize>
layout == Blocked (1):
    u32 blockElems(=4096) | u32 reserved | u64 frameCount
    frameCount × FrameEntry(48 B) = { u64 firstBlock, u64 blockCount, u64 frameOffset,
                                      u64 compSize, u64 rawSize, u32 codec, u32 reserved }
    frames 区（每帧 8 B 对齐；frameOffset 相对本区起点）
帧解压后 = 若干个 { u32 blockLen, <blockLen 字节的自描述列 blob> }
```

* 每块 = 一次独立 `encodeXxxColumn`：**自带列头/字典/首值**，所以任意一块能单独解码（不需要前面的块）。
* `kBlockElems = 4096` **与 §8.8 的 checkpoint 间隔是同一个数** —— "数据块 = 窗口 = checkpoint"三者同界。
* 帧是**独立可解压**的最小单位：`kFrameTargetRaw = 256 KB` / `kMaxBlocksPerFrame = 256`。
  2³¹ 层按 4096 切是 512,695 块，而帧表只有约 1.7 万条（≈0.8 MB）—— 这就是 §8.3 说的
  "压缩帧大小与 seek 粒度解耦"。
* `ColumnView::locateBlock()` 对帧表二分，`decodeColumnBlock(k)` **只解压 k 所在那一帧**。

### 选型：段级"实编取最小"（这是"零回归"的根据）

v2 是把**整个段**（Actions 的 6 列一起）压成一帧 zstd；实测那比"每列各压一帧"更省
（The Moon **3544 B vs 3992 B**）。所以 v3 的决策放在**段级**，两个候选都真编一遍：

| 候选 | 内容 | 段级 zstd |
|---|---|---|
| **plain** | 各列 `LegacyV2`：**裸列字节、连容器头都不加** | 照旧（= 与 v2 逐字节等价）|
| **packed** | 各列在 `SingleZstd` / `Blocked` 里取实际存储更小的 | 跳过（帧自带压缩）|

段表 `flags` 的 `kFlagLegacyColumns(0x1)` 标记"这一段是 v2 裸列布局"。

**实测（同一台机器，v2 二进制 A/B 整块回退）**：MYC **6120 B = 6120 B**、The Moon **3544 = 3544**、
QuomodocunquizE **108928 = 108928**、Unity.wav_rate **21,079,240 B**（与 v2 文档值 20.1 MB 同）。
逐字节只差 7 个字节：version、两处段 flags、以及覆盖它们的 headerCrc —— **文件大小完全相同**。

### 强制分块：`kMustBlockBytes = 128 MB`（窗口化是**要求**，不是优化）

分块把一个列切成 k 个独立可解压单元，而**独立单元必然输给一整条实心流**（熵表摊薄、
每帧各付头部与字典）。实测（`adocao pack --codec-report` 的"分块：单块 → 分块"行）：

| 谱 / 列 | 单块 | 分块 | 比 |
|---|---|---|---|
| The Moon `angleData` | 1394 B | 2970 B | **0.47×** |
| MYC `angleData` | 3055 B | 10594 B | **0.29×** |
| Unity.wav_rate `actions.val1` | 21.07 MB | 31.68 MB | **0.67×**（强制分块会让容器 +51%）|

⚠️ **§8.3 的"分段型 1.66~3.29×"是编码级口径**（§8.5 已注明"合成列、无段级压缩"）。同族合成列实测：

```
分段型 f=5% ：编码级 4,300,284 → 1,112,492 B（3.87×）｜存储级 550,464 → 548,352 B（1.00×）
分段型 f=20%：编码级 6,755,812 → 3,078,636 B（2.19×）｜存储级 1,990,637 → 2,044,164 B（0.97×）
分段型 f=40%：编码级 9,683,812 → 5,710,732 B（1.70×）｜存储级 3,901,700 → 4,082,392 B（0.96×）
```

即：**编码级收益真实（1.70~3.87×，与 §8.3 的 3.29/2.09/1.66 同档同趋势），但段级 zstd 会把它在
存储级吃掉**。所以规则是：

* 裸数据 < 128 MB：**按实编取最小** → 本轮全部真谱零回归（上面那四个数字）；
* 裸数据 ≥ 128 MB（f64 = 1600 万个值 ≈ 1600 万层）：**强制分块** —— 再大就不可能整份
  materialize，③ 的窗口化没有它无从谈起。这一档正好覆盖 D1 说的 `primer`(6.8e7) 与 2³¹。
  例外：单块 blob ≤ 64 B 的**常量级列**不强制（切了也只有一份数据，纯亏头部）。
* **中间档的已知缺口（下一步）**：想在 MYC/Unity 规模（1e7 层）也拿到可寻址性，得先做
  §8.3 的选项②（**字典段跨块共享 + 下标流按块**）—— 现在的 per-block 自包含 blob
  会在每块重付一次字典费，这正是 §8.3 预警的那一族。

### 验收与踩过的坑

* 端到端（真谱）：把阈值临时调到 1 MB，MYC 打成**真分块**容器（23,928 B / 1654 块 / 9 帧），
  `adocao image --size 64x64` 与明文谱出图 **md5 完全相同**（`8fdbed25f383aaabea32d0677f89eae1`）。
* `.adocao` 规矩照旧：每块由列编码器**自带**"编完解回来逐位比"的自检；容器再自检一次
  **整列 memcmp**，失败就退回单块 —— 并且**必须 `LOG_E`**（见下）。
* ⚠️ **坑 1：帧表的 `firstBlock` 是块号，不是元素号。** 写入方一度写的是元素下标，
  而读侧/自洽校验按**块号**二分 —— 只装 1 帧时两者都是 0，于是**单帧列全绿、多帧列全错**。
  永久用例：`multiFrame()` 用 4/16/64/200/700 块强制分块走一遍（≥3 帧才压得到）。
* ⚠️ **坑 2：容器自检失败原来是静默退回单块** —— 表现是"文件小一点、寻址悄悄没了"，
  正是本项目栽过两次的那一类。现在退回前 `LOG_E`。
* 坏数据一律干净失败（负向对照）：截断、帧字节范围越界、`blockElems=0`、未知 `layout`、
  `kind` 不符、块号越界。白噪声 / 同质滑音 / 字典主导三族都**不许**被分块选上（最坏零收益）。

## 8.12 `Derived` 段的 checkpoint（⑧ —— ✅ 已实现 2026-10-15）

> 实现：`archive/AdocaoCheckpoints.{hpp,cpp}`（计算 / 编解码 / **续算对拍**）；
> `adocao pack --checkpoints` 写出；`unpackLevel(..., DerivedInfo*)` 读回。
> 自测：`tests/adocao_checkpoints_test.cpp`（ctest `adocao_checkpoints`）。

### 记录（96 B 定长，全部小端；字段一律 **f64**，不许 f32 —— §8.8 的实测理由）

```
u32 stride(=4096) | u32 reserved | u64 count | count × 96 B
每条：u64 floor | f64 baseX,baseY | f64 cumX,cumY | f64 timeSec | f64 bpm |
      f64 radiusScale | f64 lastAngleDeg | f64 angleDirDeg |
      u32 flags | u32 sentinelRun | u8 cw | u8 pad[7]
```

`angleDirDeg`（进第 i0 层的"角度方向"，ADOFAI-JS 语义；**归一化所以有界**）、`cw`（`tileIsCW` 初值）
与 `sentinelRun`（紧跟 i0 之前连续 999 的个数）是 ③ 窗口化重算必需的三个初值 ——
§8.8 当初只列了 `bpm/timeSec`，实测下来这三样缺一不可（中旋跨窗要 `sentinelRun` 才能把
`floats[i0-1]` 推回来，见 §8.13）。

`flags` 标出"哪些分量真的算过"（稀疏）：`kCkBase / kCkCum / kCkLastAngle / kCkLastSentinel /
kCkTime / kCkBpm / kCkRadius`。读取方必须按位判，**别把 0 当真值**。

* `baseX/baseY` = `angleData` 前缀和（第 i0 层的基础位置，**不含** PositionTrack 偏移）；
* `cumX/cumY` = PositionTrack 的**继承量**（§8.8 的★：唯一"不能只靠窗口内数据算出来"的东西）；
* `timeSec/bpm` = **Timeline** 的 `tileStartTimes[i0]` / `tileBPMs[i0]` —— 用权威实现取，
  **绝不在这里重抄一份状态机**（重抄必然与生产路径漂移）。代价：pack 期要建一次 Timeline
  （约 32 B/层，实测 MYC 6.77M 层的整条验证流程峰值 RSS 1.98 GB）；
* `radiusScale` 预留（本仓库还没实现 ScaleRadius 事件），未实现时 = 1.0 且不置位；
* `flags` 还有 `kCkCw / kCkAngleDir / kCkSentinelRun` 三位（③ 用）。

### 三条不变量的落地（§8.8）

1. **闭包语义**：快照 = "`floor < i0` 的事件**全部处理完**"之后的状态。实现上快照在
   "处理第 i0 层事件**之前**"发出 —— 直接对应 §8.8 不变量 3（窗口必须自己扫 `floor == i0`）。
2. **从快照重新生成**：`verifyCheckpointResume()` 用 `ck.baseX/baseY`（而不是自己累加）起步，
   与 `applyPositionTrackOffsets` 的**同一套结合顺序**（`base + (cum + px)`）逐位对齐。
3. `justThisTile` 是**点加**：不进 `cum`，只在本层加。

### 唯一验收手段：§8.10⑥ 的逐位对拍（`memcmp`，不是容差）

```
the-moon  600538 层 → 147 条（2937 B / 容器 6528 B）｜从快照重算 602112 层，不一致 0 层
MYC      6770912 层 → 1654 条（30401 B / 容器 36568 B）｜从快照重算 6774784 层，不一致 0 层
```

命令（可重跑）：

```bash
./build/tests/adocao_checkpoints_test "<谱>"      # 单元用例 + 真谱逐条快照对拍
```

**反面对照（这条最关键）**：把快照的 `baseX` 动 **1 个 ULP**，对拍必须变红 ——
实测 1697/4096 层被判不一致（不是每一层都变，因为求和会舍入回来；所以断言是"**红**"而不是"全红"）。
没有这条，"永远绿的对拍"就等于没验（§7 别踩 2）。

其余负向对照：截断 / 连头都不完整 / `stride = 0` / `floor` 不是 stride 倍数 / `floor` 不递增
→ 全部干净失败。

### 成本与默认口径

* 实测 `MYC`：30,401 B / 6,770,912 层 = **0.0045 B/层**（80 B/条的裸记录被段级 zstd 压掉 4.3×）。
  按这个比例外推 2³¹−1 层：524,288 条 × 80 B = 42 MB 裸 → **≈ 9.8 MB**（§2 当初的估算是 19.4 MB）。
* 因为它天生是 O(n/4096) 字节，**默认不写**（`PackOptions::withCheckpoints = false`）——
  这样默认的 v3 文件仍然与 v2 **逐字节同大小**（§8.11）。要 ③ 的 O(1) seek / 窗口化就
  `adocao pack <谱> <out> --checkpoints`。
* ⚠️ 已知缺口（留给 ③）：`timeSec/bpm` 现在**算得出、存得下、验得过**，但**还没有任何消费方**
  —— 真正的窗口化加载器（③）才是它的第一个用户。在那之前，`preserved` 段（§8.7）仍未实现。

## 8.13 窗口化重算（③ 的第一半 —— ✅ 已实现 2026-10-15）

> 实现：`archive/AdocaoWindow.{hpp,cpp}`（`computeFloorWindow`）；
> `ActionIndex` 段（段 id 8）由 `AdocaoWriter` 写出、`AdocaoReader` 经 `DerivedInfo` 带回。
> 自测：`tests/adocao_window_test.cpp`（ctest `adocao_window`）。

### ③ 要解决什么

D1 要求"常驻 RSS 不随 n 线性"。位置 / BPM / 时间在加载路径里是**三条串行前缀和**，
所以"从中间某一层开始算"必须能拿到**起点状态**（②的 checkpoint 就是它）并**逐字复现算式**。

### `computeFloorWindow(settings, {checkpoint, angles[i0..], events[floor∈[i0,i1)]})`

产出一整块的 `Tile::position/direction`、`tileBPMs`、`tileStartTimes`，**不碰任何全谱数组**。
四条硬口径（每条都对应一次踩坑）：

1. **本层事件（`floor == i0`）由窗口自己处理**（§8.8 不变量 3）：继承型 PositionTrack 算进本层、
   `justThisTile` 只作用于本层、Twirl/SetSpeed **影响本层**（Timeline 是先处理事件再取状态）。
2. **PositionTrack 同层"最后一个胜出"**：`processActions` 里是 `tilePositionOffsets[floor] = {…}`
   的 map 覆盖语义，不是同层累加（我先按累加写，被对拍抓住）。
3. **浮点类型逐字一致**：`Timeline` 里 `currentBPM/angleDir/tileBPM` 都是 **float**，
   `tileStartTimes/position` 是 double。用 double 累乘 SetSpeed 会在多次乘之后差 ULP
   —— 这也意味着 checkpoint 里的 `bpm` 是"float 值存进 double"，**动 1 个 double-ULP 是看不见的**
   （反面对照因此改成动一个 float 能分辨的量，这条口径写进用例注释）。
4. **时间只认 `totalAngleAt`/`durationAt`**（生产路径），**不是** `precalcTileRange` 那份
   A/B 参考实现 —— 两份算式的浮点常量与分支并不完全相同。

### 验收：与全量加载**逐位** memcmp

| 口径 | 结果 |
|---|---|
| 合成 9000 层（纯角度 / 块边界事件 / 中旋跨窗） | 位置、方向、BPM、时间 **0 不一致** |
| `The Moon` 600,538 层 / 147 窗 | **0 不一致** |
| `MYC` 6,770,912 层 / 1,654 窗 | **0 不一致** |

**反面对照**（证明这条对拍真的会红）：`baseX` 动 1 ULP → 首层位置变红；`bpm` 变 1.5× →
BPM 与时间都变红；`cw` 翻一位 → 时间变红；checkpoint 抹掉 `time` 分量 → **明确失败**
（不许拿 0 当时间）。

命令：`./build/tests/adocao_window_test "<谱>"`（单元用例 + 真谱逐窗对拍 + 按层索引对拍）。

### `ActionIndex`（按层索引）：把"第 b 块里有哪些事件"变成 O(1)

```
u32 stride(=4096) | u32 reserved | u64 count | count × u64 firstAction
```

`firstAction[b]` = 第一个 `floor >= b*4096` 的 action 下标，**末尾多一条哨兵** = `actions.size()`；
于是第 b 块的事件区间 = `[firstAction[b], firstAction[b+1])`。前提是 actions 按 floor **非递减**
（写入方校验；不成立就不写这一段并 `LOG_W`，读者必须明确知道）。

* 实测 `MYC`：1,654 块 → 载荷 13,248 B，段级 zstd 后 **2,218 B**；
* 成本 **8 B / 4096 层 = 0.002 B/层** → 2³¹−1 层外推 **4.0 MB**（zstd 后约 0.7 MB），
  加上 §8.12 的 checkpoint（≈9.8 MB）**仍在 §2 的 19.4 MB 索引预算内**；
* 对拍：`The Moon` 147 块 / `MYC` 1654 块，区间**全部**与"全量扫描一遍 actions"一致。

### 逐层的"事件派生表"也窗口化（③ 的最后一块表）

`LevelData::processActions` 里的表分两类，**能不能窗口化取决于它是"逐层的"还是"跨层前缀"**：

| 表 | 性质 | 窗口化 |
|---|---|---|
| `tileHasTwirl` / `tileHasSetSpeed` | 逐层 | ✅ 进 `FloorWindow` |
| `atStates`（AnimateTrack）| 逐层（缺省值全来自 settings）| ✅ 进 `FloorWindow`，键是**相对窗口起点**的层号 |
| `tileBPMs` | 跨层前缀（SetSpeed 继承）| ✅ 靠 checkpoint 的 `bpm` 起步 |
| `tilePositionOffsets` | 跨层继承 + 本层点加 | ✅ 已在位置那条里处理 |
| `tileHitsounds` / `tileHitsoundVolumes` | **跨层前缀**（"当前 hitsound" = `floor <= i` 的最后一个 SetHitsound）| ❌ **故意不做**：要再往 checkpoint 加两个字段；而且它们的消费方是音频（`docs/2e9.md` 把音频列为独立的另一道墙），不是窗口化渲染 |
| `bookmarkFloors` | **全局**语义（无条件补第 0 层与最后一层做跳转目标）| ❌ 不是一个"窗口内的表" |

对拍（`adocao_window_test "<谱>"`）除了位置/BPM/时间，还比这三张表，并且**带非空转守卫**
（把"真的比过多少条"打出来，否则"0 不一致"可能只是两边都空）：
`15. Singularity` 244 块 —— Twirl 40,156 层 / SetSpeed 1,046 层 / AnimateTrack 2 条、
The Moon 147 块 —— Twirl 303,540 层 / SetSpeed 8,457 层、MYC 1654 块 —— Twirl 6,155,053 层 /
SetSpeed 314 层，**全部 0 不一致**。

**反面对照（不变量 3 的靶子）**：把 `floor == i0` 的事件整批拿掉 → 三张表**同时变红**
（Twirl/SetSpeed/AnimateTrack 都落在 4096 上；窗口不自己处理它们就丢一层）。

### `FloorWindowSource`：**从容器按块取数据**（③ 的装配）

`unpackLevel()` 是全量的（要把整份 LevelData 解出来）。窗口化要的是"给一块，别的都不碰"，
所以 `FloorWindowSource::open(data, len)` 只做三件事：拿**段视图**（新增 `getSectionView`，
段载荷**按需**解压 —— 顺带把 reader 的"一次解压所有段"改成了懒解压）、打开 6 条 action 列的
**分块列容器**、解析 `Derived`/`ActionIndex`。之后：

* `readBlock(b)` 只解压 **b 所在的那一帧**（angleData）与 action 区间覆盖到的那些帧；
* 稀疏列（`strId/val1/val2` 按**出现次数**编号）靠 `ActionIndex` 新增的三个 `used*` 起点
  做到 O(1) —— 否则只能从第 0 个 action 数起（索引条目因此是 32 B/块，实测 MYC 53 KB 裸 → 段级 zstd 后几 KB）；
* `ADOCAO_FORCE_BLOCK_KB=<n>` 是测试钩子：真谱按体积本来会选单块布局，窗口化验收必须跑在
  **分块布局**上，所以用它把强制阈值调小来造容器。
* ⚠️ **段级 layout 与列级 layout 是两件事**：列可以是分块容器，而**段**仍选 legacy
  （段级比较的是"packed vs plain+zstd"，小列/常量级列上 plain 更小）。`FloorWindowSource`
  对 legacy 段走"整段解一次再切"的退回路径（仍然正确、只是少了那一侧的内存收益），
  并由 `actionsWindowable()` 如实报出来 —— 这条是被 `15. Singularity` 的
  `readBlock(0)` 失败逼出来的（action 只有 578 条 → 段级选了 legacy）。

**验收（`adocao_window_test "<谱>"`，与全量加载逐位比）**：

| 谱 | 块数 | 角度窗口 | 事件窗口 | 位置/方向 | 时间 | BPM | 缺快照 |
|---|---|---|---|---|---|---|---|
| `The Moon` 600,538 层 | 147 | 0 | 0 | 0 | 0 | 0 | 0 |
| `MYC` 6,770,912 层 | 1654 | 0 | 0 | 0 | 0 | 0 | 0 |

### 内存：窗口化加载路径的实测（`adocao_window_test --walk <file.adocao>`）

`--walk` **不加载明文谱**，所以进程峰值 RSS 就是"文件 + 索引 + 一个窗口"的量级：

| 谱 | 层数 | 容器 | 走完累计解码 | **峰值 RSS** | 对照：全量加载 |
|---|---|---|---|---|---|
| `The Moon` | 600,538 | 10,856 B | 1.05 MB | **5.6 MB** | — |
| `MYC` | 6,770,912 | 58,344 B | 6.07 MB | **6.4 MB** | ≈1.4 GB（`docs/scale-1e8-to-2e9.md`）|

层数涨 **11×**，峰值只涨 **0.8 MB**（涨的是文件与索引本身）—— 这就是 D1 要的形状。
2³¹−1 层按这个结构外推：索引（`Derived` ≈9.8 MB + `ActionIndex` ≈0.7~4 MB）+ 一个窗口 ≈ **15 MB**。

⚠️ **边界（别读过头）**：这只证明了**加载路径**（容器 + 重算）与 n 解耦。
`LevelData` 现在仍是全量加载，按需开窗的消费方（渲染 / 剔除 / 时间线）**还没接** ——
所以 **D1 对"产品常驻内存"还不能宣称**。

## 9. v7（进行中）：自描述列式事件库

目标：容器不再为每类事件手写定长记录，而是**按 kind 分列**装下任何事件的任何字段，
做到"新增事件类型不改格式"。本节记录已落地部分与实测。

### 9.1 已落地（2026-10-22）

- `archive/AdocaoKinds.{hpp,cpp}`：kind 枚举（Bool/Int/Float/GridFloat/Enum/Color/String/Tag/Pair/
  Nested/RawJSON）与单值形态判定；**新增 kind 必须 bump version**，新增类型/字段不用。
- `archive/AdocaoSchema.{hpp,cpp}`：打包期从实际 JSON **自动发现**类型与字段，整列统计决定 kind
  （整列都在十进制网格上 → `GridFloat`；取值少且短 → `Enum`；全 hex → `Color` …），
  三态用 flags 区分（bit0 有 null / bit1 有缺失 / bit2 全 null / bit3 pair 的分量有 null）。
  序列化往返逐字节确定（同输入两次打包相同）。
- `LevelData::preserveRawJson`（**只在 pack 用**）：用 RapidJSON 捕获 `actions` 每条事件的原始切片
  与整个 `decorations` 数组；默认关，播放路径零成本。`adocao pack --schema-report` 打印统计。

1. **Pair 分量可以是字符串**：`startTile: [3333, "ThisTile"]`。之前按 `GetDouble()` 读 →

### 9.8 `FixedPointDelta`：double 列的十进制定点差分（kVersion 8，2026-10-23）

**动机**（一张 MIDI 转谱，`Tempest_hertz.adofai`）：148,644 个角度、**100,103 个不同取值**、
全是 3 位小数。double 列的候选只有 Const/Dict/Rle/Raw —— 字典 8 B/项比 Raw 还大，RLE 抓不到，
于是整列退回 **Raw 8 B/值（1.19 MB）**，段级 lzma 之后仍有 **377,000 B**。
（诊断早就写着 `建议 FixedPoint`，但编码器里**根本没有这个候选** —— 判据和实编脱节。）

**编码**（`Codec::FixedPointDelta = 8`）：找一个最小的 e（0..6），使所有值都满足
`onGrid(v, e)`：`k = round(v·10^e)` 且 `(double)k / 10^e == v`（**逐位**，不是近似）。
满足就写 `header(aux = e)` + 整数差分的 zigzag varint；解侧累加后再除以 10^e。
解码与十进制字面量的正确舍入等价，所以逐位无损由既有自检兜底（解回来 memcmp，失败退回 Raw）。

**实测**（同一张谱）：

| 编码 | 体积 |
|---|---|
| Raw 8 B/值 + lzma | 377,000 B |
| **FixedPointDelta + 列级 zstd/lzma** | **149,728 B**（2.52×） |

其余语料不受影响（2025 v6 18,352 B、MEGAMIX_2 30,992 B —— 它们的角度取值少，Dict 仍然更小）。

**wrap-aware**（同一张谱再省 30%）：角度列会在 0°/360° 处绕圈，一阶差分于是出现 ±360000
这种巨值（Tempest 有 **36,655 次**绕圈）。按周期取**最短弧**后差分立刻变小：
**149,728 → 104,600 B**。周期只在"值域跨度 ≤ 360°"时尝试，写进列头 `aux` 的**高位**
（低 8 位仍是 e）—— 于是没有任何旧文件因此解错：`period = 0` 就是原来的行为。
解侧：`prev = wrap(prev + Δ)`，再除以 10^e。

**版本**：新增 codec 是**读侧不兼容**的改动 → `kVersion` 7 → **8**。旧构建读新文件会明确报
"未知 codec"，不会给出半截数据。

**顺带修的两个坑**（都是这张谱暴露的）：
1. 去重后**一条事件都不剩**时（整张谱只有 `Pause`，全由 v6 段承载）`pack --v7` 会报
   "事件列分块失败" —— 现在直接跳过 v7 段，并在自检里认这种"无需 v7"的情况；
2. `adocao_blocked` 的 fixture 原来用 `round(u·1e6)/1e6`（正好落在十进制网格上），
   FixedPointDelta 一上线它就赢过"分块"，用例覆盖不到分块布局了 —— 改成全精度 uniform 值。
